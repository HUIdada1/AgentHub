## 0.5 核心判据：什么下沉、什么必须留在外面、什么必须修逻辑

> 用户原话："一部分内容可以稍微做深一点，可能有一些是必须的，不然在配置里面他也用不到。"
> 这是本方案**最重要的判定标准**，先立规矩，后面 Phase 3/4/5 全部按它执行。

### 铁律：**主界面只回答「现在怎么样」+「我该点哪里」；解释与参数可以下沉。但任何「用户能做决定的操作」和「唯一的入口」绝不下沉。**

### 三分法（逐条判定，不做一刀切）

| 类别 | 判定问题 | 处置 | 记忆仓库的具体例子 |
|---|---|---|---|
| **A. 决策信息** | 用户会据此做动作吗？ | **必须留在主界面** | 待确认条数、索引是否一致、Agent 是否真的连上、今日新增 |
| **B. 解释信息** | 只是帮用户理解，不据此操作？ | **可下沉**（`MemHelp` 气泡 / 折叠区），**但首次出现处必须留一个入口** | "L1/L2 是什么"、"为什么索引要重建"、"BM25 是什么" |
| **C. 参数 / 开关** | 用户需要调吗？ | 见下方 §0.5.1 逐项判据 | 权重、阈值、批量、token 上限 |
| **D. 排障工具** | 只在该功能坏了才会用？ | **可下沉到折叠区，但必须保留可达路径 + 异常时自动浮出** | 分词结果、评分分解、WAL 体积、digest 预览 |
| **E. 唯一入口** | 不点它就完不成某事？ | **绝不下沉**，即使它看起来"很技术" | Agent 注入按钮、模型 API Key 填写、记忆根目录选择、导入来源路径 |

### §0.5.1 配置项判据（解决"有些必须的，不然在配置里他也用不到"）

**每一项配置按下表逐条打分，落在哪档就进哪档：**

| 判据 | 归入 |
|---|---|
| ① **不填就无法使用核心功能**（如 `storage.root`、模型 `apiKey`、`agents.enabled`） | **常显（basic）**，且必须给默认值，让"不填也能跑" |
| ② **默认值已是最优，改了大概率变差**，但用户可能会好奇（如所有权重、阈值、半衰期） | **折叠（advanced）**，折叠标题必须写"默认值已最优，无需修改" |
| ③ **改错会影响稳定性**（如 `index.debounceMs`、`import.batchSize`、`sync.packSizeLimitMB`） | **二次确认（internal）** |
| ④ **用户会主动想做决策**（如 `auto.enabled` 要不要开、`dedup.l4` 要不要花 token、回收站保留几天） | **常显（basic）** |
| ⑤ 只是**显示偏好**（如 `ui.pageSize`、`ui.realtimeRefresh`） | **常显（basic）**，但要放在配置页最下方 |

> **关键纠正**：`ui.defaultTab`（默认页签）看起来是"显示偏好"，但用户**几乎不需要改**（因为页签只有 3 个了，改不改无所谓）→ 归 **advanced**。
> `search.synonymsEnabled` 看起来是"技术开关"，但用户**搜不到东西时会去关它**（怀疑是它捣乱）→ 归 **basic**。
> **判据是"用户会不会主动想动它"，不是"它长得像不像技术项"。**

### §0.5.2 "主界面深度"的三档标准（解决"有些可以做深一点"）

不是所有页都要瘦身到一样浅。记忆仓库按**使用频率 × 心智负担**分三档：

| 档 | 页面 | 深度标准 | 实测依据 |
|---|---|---|---|
| **浅（首屏级）** | `DashboardView`（7 按钮 / 10 卡片）、`BrowseView`（17 按钮 / 4 输入 / 2 分段） | 首屏一屏之内看到"结论 + 主行动"；其余折叠 | 这两页是 90% 时间的着陆页 |
| **中（任务级）** | `ProjectsView`（3 按钮 / 1 卡片）、`AgentsView`（14 按钮 / 8 卡片）、`AutoView`（8 按钮 / 5 卡片）、`SyncView`（9 按钮 / 9 卡片）、`ImportView`（15 按钮 / 11 卡片） | 允许完整任务流，但**每个卡片只做一件事**；危险动作确认 | 这三页用户是带着明确目的来的 |
| **深（排障级）** | `IndexView`（6 按钮 / 6 卡片）、`ProfileView`（7 按钮 / 2 卡片） | **可以很深**，允许暴露分词/评分/WAL；但默认全部折叠，且顶部写"平时不用来这页" | 只有出问题才来 |

> 实测：`AgentsView` 14 个按钮、`ImportView` 15 个按钮、`DashboardView` 10 张卡片 —— 这三处是"繁琐"的重灾区，优先处理。
> `MemHelp` 覆盖率实测：`BrowseView` 8 处、`IndexView` 7 处尚可；**`MemoryDetailDrawer`（0）/ `MemoryHeatmap`（0）/ `MemDialog`（0）完全无解释** —— 这是"看不懂"的盲区，Phase 3 必须补。

### §0.5.3 必须修的逻辑（不能靠"藏起来"掩盖）

> 用户说"有些逻辑的地方是有问题的"。以下情况**即使把界面藏得再干净也必须修逻辑**，因为它们是"点了没反应/数字自相矛盾"：

- 数字自相矛盾（§2 的 A1：红点与面板计数不同源）
- 跳转静默失败（A4）
- 点击后状态不刷新（A6：处理完红点延迟）
- 展示过期数据（A7：校验结果不跟刷新）
- 样式假设与实际用法不符（A3：`.is-2nd` 死代码）

**判据**：凡是"用户无法从界面判断自己有没有操作成功"的，一律归为逻辑缺陷，必须修，不得下沉掩盖。

### A 类 · 记忆仓库的真实逻辑缺陷（必须修，附证据）

| # | 问题 | 证据 | 影响 |

| **A1** | **`MemReviewPanel` 的 `total` 与页签红点口径不一致** | `MemReviewPanel.vue` `const total = computed(() => counts.supersede + counts.classify + counts.dedup)`，而 `counts` 来自 `refresh()` 的**三个独立接口成功才计数**（`.catch(() => {})` 静默吞错）；`BrowseView.vue` 的 `reviewTotal = mem.pending.browse`（来自 `memoryStats().pending`）。两者是**不同数据源**，任一接口失败就出现"红点显示 5 条、面板说 0 条待你点头" | 用户看到自相矛盾的数字，信任崩塌 |

## 3. 记忆仓库的"简约化"设计原则

> **铁律**：主界面只回答三件事 ——「记了多少 / 好着吗 / 我现在该点哪里」。所有解释、参数、排障一律下沉。

**三层披露模型**（记忆仓库专用）

| 层 | 位置 | 内容 | 例子 |
|---|---|---|---|
| **L0 结论** | 仪表盘顶部一行 | 一句话状态 + 一个主行动 | 「已记 1,240 条 · 一切正常」+「新增一条记忆」 |
| **L1 关键数** | 仪表盘 KPI（不超过 4 张） | 只有用户会做决策的数字 | 记忆总数 / 活跃 Agent / 今日新增 / 待确认 |
| **L2 明细** | 各功能页（浏览/项目/索引...） | 可操作的数据 | 记忆列表、项目卡、冲突 diff |
| **L3 排障** | **折叠区 / 抽屉 / 「高级」面板**，默认全部关闭 | 分词、评分分解、WAL 体积、79 项配置里 60 项 | 「检索调试」「digest 预览」「高级项」 |

**配置项三分法**（解决 B5 的根因）：把 79 项按"用户是否需要碰"分成三档，**标记写在 schema 里（后端），而不是前端手写 Set**：
- `tier: "basic"`（约 15 项）：配置页默认可见。如 `storage.root`、`auto.enabled`、`deep.enabled`、`ui.pageSize`、`agents.enabled`。
- `tier: "advanced"`（约 40 项）：默认折叠进「高级设置」。如所有权重、阈值、批量、并发。
- `tier: "internal"`（约 24 项）：**默认隐藏**，需要点「显示内部参数」二次确认。如 `index.debounceMs`、`search.graphExpansionMax`、`dedup.l2.wDice`。

### Phase 0 · 记忆仓库专属验证脚手架

**目标**：先建"尺子"。后续每个 Phase 都用它。**不改任何业务代码。**

**任务**

1. 新建 `tools/verify/` 目录，写以下脚本（**全部纯 Node，零 GUI**）：

   - **`tools/verify/m-plumbing.cjs`** — 记忆仓库管道一致性
     - 校验四方命令清单，**只针对 `memory_*` 前缀**：
       - A：`grep -oE 'ipcMain\.handle\("(memory_[a-z_0-9]+)"' electron/backend/memory/index.cjs`
       - B：`electron/preload.cjs` 里 `memory_` 开头的白名单项
       - C：`src/api/ipc.ts` 里所有 `call<...>("memory_..."` 的命令
       - D：`src/api/mock.ts` 里所有 `case "memory_..."` 的命令
     - 断言：`A == B`；`C ⊆ A`；`C ⊆ D`。
     - 当前基线：`A == B` 应已成立（全项目层面已验证过 251=251）。**若 C 有 D 中缺失的，脚本输出清单**——这可能是记忆模块自己的 mock 缺口。

## 7. 风险与不做的事

**风险**
1. **Phase 4 把 9 个页签降到 3 个**会改变用户习惯。缓解：`secondary` 页仍可从仪表盘的 `MemMorePanel` 一步到达；`ui.defaultTab` 的 9 个 option 全部保留，老配置不受影响（**必须在 Phase 4 验证此点**）。
2. **Phase 5 改 `dedup.l4.enabled` 默认值**会让老用户行为变化。缓解：**只改默认值，不做迁移**——已有配置文件里显式写了 `true/false` 的，`mergeConfig` 会保留其原值，不受影响。执行时必须验证这点。
3. **Phase 1 摘 `memory-nav.ts` 是多一层抽象**。收益：纯代码可验证；成本：多一个文件。**若 Phase 0 的 `m-nav.cjs` 证明可以不用抽象就能验证**（比如直接对 `pickReviewTab` 这段纯逻辑抽函数即可），则只抽 `pickReviewTab`，不抽整个 `resolveMemNav`。执行时自行判断，但**必须留下可验证的纯函数**。

**明确不做**
- 不改技能仓库 / 用量统计 / 反代网关任何文件。
- 不改记忆文件的 frontmatter 布局、目录结构、SQLite 表结构、WebDAV 远端格式。
- 不重构 `service.cjs` / `index.cjs` 的后端数据流（只做 A8 所需的确认与（如必要的）最小补丁）。
- 不删 `memory-index-bench*.cjs`（仅建议）。（该轮约束；2026-10-03 的专项审查已按此建议完成清理：删 8 个中间迭代，保留 2 个基准脚本）
- 不为记忆模块引入新的 UI 框架或组件库。
- 不做中英双语（只做中文术语降噪）。

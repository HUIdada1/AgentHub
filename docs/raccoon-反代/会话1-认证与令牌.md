## 1. 认证流程（文字时序）

### 1.1 登录（仅 Electron 主进程发起，box-agent 不参与登录）

```
1. 渲染层(登录墙) --IPC desktop-auth:start-login-from-wall--> 主进程
   （main.js:4690；校验渲染层 URL 必须可信：app://raccoon 或 http://localhost:44218）
2. 主进程 shell.openExternal("https://xiaohuanxiong.com/code/authorize?login_source=desktop&appname=办公小浣熊客户端")
   （desktopLogin.js:9-23，DESKTOP_AUTH_PATH='/code/authorize'）
3. 网页端登录完成 -> 深链回调 office-raccoon://auth/callback?code=<一次性授权码>
4. 主进程 queueDesktopLogin() 暂存 code（desktopLogin.js:103；仅保留最新 code，兑换中不覆盖）
5. finishDesktopLogin() -> POST {AUTH_API}/login_with_authorization_code
   body: {"authorization_code": "<code>"}   15s 超时（desktopLogin.js:40-58）
6. 响应 data.access_token + data.refresh_token(+office_identity/org_name/org_role)
   -> updateDesktopAuthState() 写入 auth.json（desktopLogin.js:93-100）
```

- 授权码错误码：`200035` = 授权码不存在/过期/已消费（desktopLogin.js:16 `AUTHORIZATION_CODE_NOT_FOUND`）。授权码是**一次性**的（被消费即失效），这是登录侧唯一明确的"互踢"。
- 登录成功后没有周期性刷新任务：box-agent 与 Electron 都是**惰性刷新**（用到时才刷新），不存在后台定时器主动续期（全仓 grep `setInterval/setTimeout` 无认证刷新；唯一定时器是可信设备心跳 60s）。

### 1.2 请求时取 token（box-agent 惰性刷新路径）

```
LLM 请求 -> LLMClientBase._auth_headers()  (llm/base.py:69)
  -> ensure_hosted_auth_ready(api_base, auth_file, explicit_token=...)  (auth.py:154)
     1. explicit_token 非空 -> 直接用（透传，不刷新）
     2. api_base 非小浣熊域名 -> 只读文件 token，不刷新
     3. 文件里 access 与 refresh 都为空 -> resolve_auth_token() 环境变量兜底；
        仍空 -> 抛 HostedAuthRequiredError('未登录，请通过客户端登录后再试')
     4. -> refresh_hosted_auth_token_if_needed(...)  (auth.py:196, force=False)
```

### 1.3 惰性刷新判定（`refresh_hosted_auth_token_if_needed`，auth.py:196）

```
current_time = int(time.time())
expiry = _jwt_expiry(current_token)      # 本地解 JWT payload.exp，不验签
if not force and current_token and (expiry is None or current_time + 300 < expiry):
    return current_token                  # 还有效（>300s 才到期）直接用，不发请求
# 需要刷新：
rejected_token = rejected_token or current_token
async with _refresh_lock(auth_file):     # 同进程同事件循环按文件路径互斥
    重读文件 -> current_token              # 可能已被别人刷新
    if force and current_token and current_token != rejected_token:
        return current_token              # 已被并发刷新，直接复用新 token
    再做一次 300s 窗口判定，仍要刷：
    refresh_token = state.get('refresh_token')
    if not refresh_token:
        force -> 抛 HostedAuthRequiredError('登录态已过期，请重新登录')
        非 force -> 返回 current_token（带死也要返回，不刷）
    POST {scheme}://{netloc}/api/web/auth/v1/refresh
        body = {"refresh_token": refresh_token}   # 仅一个字段，无 client_id/secret
        httpx.AsyncClient(timeout=15.0)
    网络错误(httpx.HTTPError):
        非 force 且 access 还没过期 -> 静默返回旧 access_token（容忍抖动）
        否则 -> 抛 HostedAuthRefreshError('登录态刷新失败：<exc>')
    HTTP 401 -> 抛 HostedAuthRequiredError('登录态已过期，请重新登录')
    其他非 2xx -> 若旧 access 未过期返回旧 token，否则抛 HostedAuthRefreshError('登录态刷新失败（HTTP N）')
    payload = response.json()  # 非 JSON -> HostedAuthRefreshError('服务器响应不是有效 JSON')
    data = payload.get('data')
    next_access  = data.get('access_token')
    next_refresh = data.get('refresh_token')
    # 校验新 access：空串 -> 抛'服务器返回的 token 不可用'；
    # 有 exp 且 current_time+300 >= exp -> 同样抛不可用
    next_state = dict(旧state); 删掉 token/auth_token 键; next_state['access_token']=next_access
    if next_refresh: next_state['refresh_token'] = next_refresh   # 没返回就保留旧的
    _write_auth_state(path, next_state)     # 原子写 + chmod 0o600
    return next_access
```

### 1.4 401/200003 触发强刷重试（`LLMClientBase._call_with_hosted_auth_retry`，llm/base.py:106）

```
call_once() 失败 ->
  若 uses_file（auth.json 托管模式）且 is_hosted_provider_auth_rejection(e):
     # 判定条件 = HTTP 401 或 错误码 200003（数字/字符串）或
     #           haystack 含 '200003'/'authorization_verify_error'
     # （llm/error_messages.py:371，is_hosted_provider_auth_rejection）
     从失败的 request.headers['Authorization'] 剥出 rejected_token（'Bearer '前缀后）
```

另有细节：`call_once` 内部（llm/base.py:114-135）对**非流式**响应还会额外读 JSON body，若 `payload.code in (200003, '200003')` 则主动抛 `HTTPStatusError('provider authorization_verify_error (200003)')` / `ValueError`，把"HTTP 200 但 body 报错码"也纳入重试通道。

## 2. token 生命周期表

| 维度 | access_token | refresh_token |
|---|---|---|
| 签发 | `login_with_authorization_code`（登录）或 `refresh`（续期）响应 `data.access_token` | 同上，`data.refresh_token` |
| 算法/格式 | JWT HS256（payload: `exp/iss/jti/name/nation_code/nbf/owner_type/sid`） | 同左 |
| **实测有效期** | `exp-nbf = 10805s ≈ 3h`（auth.json 实测：nbf 2026-09-21 02:41:13Z，exp 05:41:18Z） | `exp-nbf = 2592005s ≈ 30d`（同文件实测，exp 2026-10-21） |
| 存储 | `~/.box-agent/config/auth.json` 的 `access_token`（0600 权限） | 同文件 `refresh_token` |
| 失效检测 | 客户端本地解 `exp`，提前 300s 视为"需刷新"（`AUTH_REFRESH_WINDOW_SECONDS=300`，auth.py:30；scheduleAuth.js:21） | 本地不解 exp；只在刷新请求被 401 拒绝时才确认失效 |
| 刷新方式 | 用 refresh_token POST `/api/web/auth/v1/refresh`（30 天内任意时刻可刷） | 每次刷新若服务端返回新 refresh_token 就覆盖；不返回则保留旧的（auth.py:297-298；scheduleAuth.js:231；scheduleAuth.test.js:131 用例明确"keeps the existing refresh token"） |
| 刷新后旧值 | 客户端**不主动作废**旧 access_token；服务端是否作废旧 access **未确认，需抓包验证** | 若服务端未旋转（响应无新 refresh），旧 refresh 继续有效；若旋转，旧的是否立刻失效**未确认，需抓包验证** |
| 本地清除 | `clearBoxAgentAccessToken()` 只删 access（boxAgentAuthFile.js:98）；`clearBoxAgentDesktopAuthState()` 整文件删（boxAgentAuthFile.js:86） | 同上；`desktop-auth:clear` IPC（main.js:4746）只做**本地删除，无服务端注销** |

### JWT payload 里的关键字段（实测样本）

```
sid: "web65b81a6178ade6f66ba05a74d4d-c57d-4825-90a9-4eb1de1ffb8e"
```

access 与 refresh 的 `sid` **完全相同**——这是服务端"登录会话"标识。`iss: "6f66ba"` 是账户 ID 的十六进制缩写（boxAgentConfig.js:982-995 `hexIdToDecimalString` 把 hex `iss/sid` 前缀转十进制 user id）。一次登录 = 一个 sid；sid 是服务端做"多端会话管理/踢下线"的天然抓手（客户端无法感知，服务端可以按 sid 作废全部 token）。

## 3. 凭据存储与读取优先级

### 3.1 auth.json 结构（实测 + 读写双方代码）

```json
{
  "access_token": "eyJ...",
  "refresh_token": "eyJ...",
  "office_identity": "personal"          // 或团队版 org code（ASCII 可打印）
}
```

- 路径：`%BOX_AGENT_CONFIG_DIR%/auth.json`（Electron 侧，boxAgentAuthFile.js:28）= 默认 `~/.box-agent/config/auth.json`；box-agent 侧解析为 `$BOX_AGENT_HOME/config/auth.json`（user_paths.py，`state_path('config/auth.json', override)`；BOX_AGENT_HOME 缺省 `~/.box-agent`）。
- ⚠️ 两侧环境变量名不同：Electron 认 `BOX_AGENT_CONFIG_DIR`，box-agent 认 `BOX_AGENT_HOME`（且要求绝对路径、不能是系统根/家目录祖先）。号池做多目录隔离时两个都要设，不能只设一个。
- 写文件两边都是"临时文件 + 原子 rename/replace"：Electron 用 `{authPath}.{pid}.tmp`（boxAgentAuthFile.js:67-73），box-agent 用 `.{name}.{uuid4}.tmp` + `os.replace`（auth.py:111-120），都会 chmod 0o600。**并发写不会损坏文件，但后写覆盖先写**。
- ⚠️ 字段保留差异：box-agent `_write_auth_state` 是 `dict(旧state)` 再改，**保留未知字段**；Electron `writeBoxAgentDesktopAuthState` 只回写它认识的 5 个键（access/refresh/office_identity/office_org_name/office_org_role），**会丢弃 auth.json 里的未知字段**。号池若想在 auth.json 里塞自定义元数据（账号别名等），会被 Electron 一次刷新抹掉——元数据必须放旁边的独立文件。

### 3.2 token 读取优先级（box-agent `resolve_auth_token`，auth.py:303）

1. 显式 `explicit_token`（调用方传入，config 的 `auth_token`）
2. auth.json 文件：依次看 `token` → `access_token` → `auth_token`（auth.py:28 `AUTH_TOKEN_FILE_KEYS`，首个非空胜出）
3. 环境变量：`BOX_AGENT_AUTH_TOKEN` → `OFFICEV3_AUTH_TOKEN` → `RACCOON_ACCESS_TOKEN` → `RACCOON_TOKEN`（auth.py:21 `AUTH_TOKEN_ENV_VARS`）；但注意第 2 步文件里有值就不会走环境变量，且 `configured_box_agent_home()` 非空时直接返回空串（auth.py:315-316 的 `if configured_box_agent_home(): return ''` 分支在文件无 token 之后）

`ensure_hosted_auth_ready` 里只有当**文件里 access 与 refresh 都为空**时才回落环境变量；有 refresh_token 就总是走刷新，环境变量兜底不生效。

### 3.3 Authorization 头的附加规则

- `bearer_auth_headers`（auth.py:325）：已有 `Authorization` 头时不覆盖（用户自配 provider/MCP 凭据优先）；只对目标 URL 附加：`should_attach_auth_header` 要求 hostname == `xiaohuanxiong.com`、以 `.xiaohuanxiong.com` 结尾、或 == `10.158.136.99`（auth.py:29 `AUTH_HEADER_HOST_SUFFIXES`）。
- 团队版额外头：`X-Org-Code: <office_identity>`，仅当 office_identity 非 'personal' 且全 ASCII 可打印时附加（auth.py:140-151 `read_auth_org_code`；llm/base.py:85-87）。

## 4. 互踢与并发结论（号池多开的核心问题）

### 4.1 refresh_token 是否旋转（rotation）

- 客户端两侧都实现了"服务端返回新 refresh 就覆盖、不返回就保留旧的"（auth.py:297-298、scheduleAuth.js:231、测试 scheduleAuth.test.js:131）。
- 也就是说**协议支持旋转，但客户端无法证明服务端一定旋转**。每次刷新是否签发新 refresh_token、旧 refresh_token 是否在旋转后立即作废——**未确认，需抓包验证**（连续刷新两次，第二次用第一次的旧 refresh 观察是否 401）。

### 4.2 新旧 access_token 是否并存

- 客户端在"强刷"路径里显式区分 `rejected_token` 与新 token（auth.py:227、232；llm/base.py:147-151），并容忍"文件里已是新 token"的情况——说明设计上**预期多个使用方并发刷新同一文件**。
- 旧 access 作废与否客户端不感知；`sid` 不变的情况下，JWT 无状态验签，旧 access 在其 3h exp 之前理论上仍可用——**未确认，需抓包验证**（刷新后立刻用旧 access 调 `/api/web/points/v1/balance` 看是否 200003）。

### 4.3 多端登录互踢

- 客户端代码里**没有任何"被踢下线"的检测逻辑**：没有轮询会话状态，没有监听 401 之外的踢出信号。被踢的唯一表现就是 refresh 返回 401 → 本地抛"登录态已过期，请重新登录"。
- 桌面端有**可信设备绑定**（`devices_current_bind` + 60s 心跳），服务端返回 `device_session_mismatch` 错误码时桌面端进入 `device_mismatch` 终态（desktopTrustedDeviceManager.js:286-288）。这证明服务端**会做"会话(sid) ↔ 设备(client_device_id)"绑定校验**。
- 但注意：该绑定只出现在**移动端连接器/relay 链路**（remote/connectors/mobile/*），box-agent 的 LLM 请求路径不携带心跳、也不带 `X-Client-Device-ID`（那是可信设备接口的头，不是 LLM 头；LLM 只带 `x-client-device-id` 小写指纹头，仅作遥测用途）。**号池的反代只调 LLM/points 接口时不会触发设备绑定校验**。
- 结论（静态证据范围内）：
  - **同一账号在多个 box-agent 实例间"同时各用各的 token"：能多开**。依据：刷新接口幂等（只凭 refresh_token 换 token）、客户端容忍并发刷新同一文件、无会话独占检测。
  - **同一账号在两个客户端各自"登录"（两次网页登录）：大概率会互踢，但程度未确认**。两次登录产生两个不同 sid；服务端是否允许同账号多 sid 并存、`devices_current_bind` 是否限制设备数——**客户端无代码可证，需抓包/实测**。
  - 号池实践含义：**一个号登录一次，把 refresh_token 复制到 N 个隔离目录共用**，比"一个号在 N 台机器各登录一次"安全得多（后者每个 sid 独立、可能互相顶掉；前者只有 refresh 旋转这唯一冲突点，且下一个刷新者会立刻自愈）。

### 4.4 刷新并发安全

| 场景 | 机制 | 结论 |
|---|---|---|
| box-agent 同进程并发 | `_refresh_lock`：按 `(event_loop, auth_file绝对路径)` 的 `asyncio.Lock`（auth.py:42-44、105-108）；锁内重读文件，`force` 时若文件里 token 已 ≠ rejected_token 直接复用（auth.py:232） | **安全**，单飞 + 双检 |
| Electron 主进程并发 | 模块级 `refreshInFlight` Promise 单例（scheduleAuth.js:27、100-109） | **安全**，单飞 |
| 跨进程（box-agent × Electron，或两个 box-agent 实例） | **无锁**。各自读-刷-原子写。风险窗口：A 读到旧 refresh 发出请求的同时 B 已刷新并写入新 refresh；若服务端旋转 refresh，A 的旧 refresh 请求会 401 → A 抛 HostedAuthRequiredError（force 路径）或静默用旧 access（非 force 且未过期） | **基本安全但有旋转竞态**：文件原子写保证不损坏；唯一坏情况是旋转后某一方拿着"已作废的旧 refresh"刷出 401。客户端对 force 路径直接抛"重新登录"，不会自动重试——号池实现要兜住这个 case（401 后重读文件再试一次） |

## 5. 失效条件与客户端反应

| 触发 | 服务端表现 | 客户端反应 | 是否需重新登录 |
|---|---|---|---|
| access 过期（>3h） | 401 或 body `code:200003`（authorization_verify_error） | 惰性刷新或 401 强刷后重试一次；成功则透明 | 否（refresh 有效时无感） |
| refresh 过期（>30d）或授权码复用 | refresh 返回 401；登录 code 复用返回 `200035` | 抛"登录态已过期，请重新登录"；Electron `prepareBoxAgentAuthForWarmup` 遇此会 `clearBoxAgentAuth()`（清 access）并把状态标记 missing，渲染层回登录墙（scheduleAuth.js:215-217、main.js:4778-4780） | **是** |
| 刷新网络抖动/5xx | 非 401 的其他 HTTP 错误 | 旧 access 未过期就静默继续用；已过期才抛 HostedAuthRefreshError | 否（容忍抖动） |
| 服务端返回的 access 不可用（空或 300s 内到期） | 200 但 data 异常 | 抛"服务器返回的 token 不可用"，**不写文件**，旧 token 保留 | 否，下次请求还会再刷 |
| 本地文件损坏/非 JSON | — | `_read_auth_state` 吞掉返回空 dict（auth.py:61-64），表现为"未登录" | 是（文件没了） |
| 设备绑定失效 | `device_session_mismatch`（仅移动端连接器链路） | 桌面端进 `device_mismatch` 终态，停止心跳 | 需重新绑定设备；**不影响纯 LLM 调用** |
| 主动登出 | 无服务端注销端点被调用 | `desktop-auth:clear` 只删本地文件（main.js:4746） | token 在服务端继续有效直到自然过期 |

## 6. 号池多账号认证管理方案

基于以上事实，给出可直接落地的设计。目标：N 个账号、每号独立隔离、并发刷新安全、失效可兜底。

### 6.1 存储隔离：每号一个 BOX_AGENT_HOME

```
pool/
  accounts/
    acc-01/                  # BOX_AGENT_HOME
      config/auth.json       # {access_token, refresh_token, office_identity}
      sessions/  memory/     # box-agent 其它状态自动落在同目录
    acc-02/ ...
  pool.json                  # 号池索引（见 6.3）
```

- 依据：box-agent 的 `state_path` 以 `BOX_AGENT_HOME` 为根（user_paths.py:16-27），auth.json、会话、记忆全部随目录隔离，天然不串号。
- **不要用**环境变量注入 token（`RACCOON_ACCESS_TOKEN` 等）当主存储：那是只读兜底，不能刷新回写，refresh_token 也没法通过环境变量提供。
- ⚠️ 账号元数据（别名、备注、状态）**不要写进 auth.json**——Electron 侧刷新会抹掉未知字段（见 3.1）。元数据放 `pool.json`。

### 6.2 token 池数据结构（`pool.json`）

```jsonc
{
  "accounts": [
    {
      "id": "acc-01",
      "label": "小浣熊A号",
      "home": "accounts/acc-01",            // BOX_AGENT_HOME 相对路径
      "sid": "web65b81a61...",              // 从 access_token payload 解出，用于账号识别/去重
      "name": "RaccoonSofia",               // JWT payload.name
      "status": "ready",                    // ready | refreshing | degraded | expired
      "access_exp": 1789969278,             // 本地解码缓存
      "refresh_exp": 1792550478,
      "last_refresh_at": 1789958473,
      "last_error": null,
      "generation": 3                        // 每次成功刷新 +1，用于"串号自检"
    }
  ]
}
```

### 6.3 刷新调度

- **调度器集中刷新**（推荐）：池管理器每 60s 扫一遍 `pool.json`，对 `access_exp - now < 600s` 的账号逐号执行刷新（直接调 `POST /api/web/auth/v1/refresh`，协议只有一个字段，无需起 box-agent）。刷新结果原子写回该号 `config/auth.json`（复刻 `_write_auth_state`：临时文件 + os.replace + 0o600）。
  - 好处：账号未用时也能提前续期，业务请求永远拿到"ready" token，避开 box-agent 惰性刷新的首请求延迟（15s 超时）。
- **单飞防并发**：池管理器对每号维护内存锁（等价 `refreshInFlight`）；同时 box-agent 自身的 `_refresh_lock` 兜底进程内并发。**跨进程必须只留一个刷新者**：选定"池管理器独占刷新"，box-agent 侧保持惰性兜底即可（box-agent 非 force 路径在旧 access 未过期时会静默容忍，不会乱刷）。
- **防串号自检**：每次刷新后解码新 access 的 `sid`，与该号登记的 `sid` 比对；不一致说明服务端换了会话（异常），把账号置 `degraded` 并告警。`sid` 稳定相同是"没被顶号"的最强本地证据。
- **写文件时保留 refresh 兜底**：新响应没返回 refresh_token 时保留旧值（照抄两侧实现），不要误删。

### 6.4 失效兜底策略

| 事件 | 检测 | 兜底动作 |
|---|---|---|
| refresh 401 | 刷新响应 HTTP 401 | 标记 `expired`，立刻从可用池摘除；该号进入"待重登"队列（需要人工/扫码重新登录一次） |
| LLM 200003/401 且刷新后仍失败 | 业务层拿到 HostedAuthRequiredError | 同上，标记 expired |
| 刷新 5xx/超时 | 网络错误 | 指数退避重试（60s/5min/30min），旧 access 未过期期间继续可用；不降级状态 |
| refresh 临近过期（<3d） | 本地解 refresh `exp` | 提前告警，提示运营重新登录补票 |
| 文件消失/损坏 | 读 auth.json 失败 | 等价 expired |
| sid 变化 | 每次刷新后比对 | `degraded`，人工确认是否被踢 |

### 6.5 多开建议（结合第 4 节结论）

- **推荐模式：一号一目录，refresh_token 不共享给第二个活跃刷新者**。即：号池管理器是唯一刷新者；业务侧每个号只起一个 box-agent（或反代实例），各用各目录。**能多开**。
- **避免：同号在两个独立登录会话（两个 sid）同时跑**。客户端无多会话协调代码，服务端有 sid 级会话管理抓手，是否互踢未确认但风险高。
- 若必须"一号多并发实例"：共享同一个 BOX_AGENT_HOME（同一份 auth.json）并保证只有一个刷新者；其余实例把 `refresh_token` 字段**从它们的视角屏蔽**（用只读快照 token + 环境变量注入 access），让它们永远不触发刷新——box-agent 对显式 token 会直接透传不刷新（auth.py:171-173）。

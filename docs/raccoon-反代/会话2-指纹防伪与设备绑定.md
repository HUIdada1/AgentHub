# 会话 2：调用指纹 / 防伪 / 设备绑定 独立审查

> 审查范围：Electron 主进程指纹注入、box-agent Python `client_info`/`auth` 层、渲染层指纹、受信设备绑定全流程、遥测、号池反关联设计。
> 所有结论均基于反汇编/解包后的真实代码，证据附文件路径+行号或反汇编片段。找不到的明确标"未确认/需抓包验证"。

---

## 0. 总结论（先看这段）

1. **防伪强度：低**。无任何请求签名 / HMAC / nonce / timestamp / 防重放机制，无证书 pinning，无代码混淆。整个防伪体系就是 **JWT access_token + x-client-device-id + 受信设备绑定** 三件套，全部可静态复刻。
2. **设备指纹是随机 UUID，不是硬件派生**。`clientDeviceId` 由 `crypto.randomUUID()` 生成，持久化在 `AppData/Roaming/office-raccoon/desktop-device-identity.json`，删除即重新生成一个新随机 UUID。换号时给每个号配一个独立 UUID 即可完全隔离。
3. **x-client-* 六头只在指向 `*.xiaohuanxiong.com` 时附加**，清洗规则仅是 ASCII 可打印字符过滤 + 256 字节截断。取值全部来自静态常量或 `os` 模块，无硬件采集。
4. **渲染层没有实质指纹采集**。代码里的 "fingerprint" 全是编辑器语法高亮关键字和一个 FNV-1a 文本 hash 工具（用于会话内容去重），**不存在 @fingerprintjs 浏览器指纹上报**。遥测 `machine_id` 是**全局硬编码常量** `simulator-f31d...`，所有客户端相同，不构成区分维度。
5. **号池反关联的暴露面非常窄**：真正会泄露"同源"的只有 `出口 IP` + `x-client-device-id` + `心跳时序` + `X-Request-Id 时钟` 四项。把这四项按号隔离，风控能拿到的"同源证据"就只剩下 IP。

## 1. x-client-* 六个头：精确取值来源与清洗规则

### 1.1 生成位置
六头由 box-agent（Python）在每次 LLM 请求时生成，仅当目标 URL 是 `xiaohuanxiong.com` 或其子域时附加。

证据：
- `pyz/modules/box_agent/client_info.pyc` 中 `should_attach_client_headers(url)`：
  - 常量：`'.xiaohuanxiong.com'`、`'xiaohuanxiong.com'`、`frozenset({'http','https'})`
  - 逻辑（反汇编）：`urlparse` 取 hostname → `lower().rstrip('.')` → 判断是否 `== 'xiaohuanxiong.com'` 或 `endswith('.xiaohuanxiong.com')`，且 scheme ∈ {http, https}。
  - docstring：`'Limit product metadata to the Raccoon domain and its subdomains.'`

### 1.2 六个头的真实取值

头名在 `client_info.pyc` `headers_for_url` 的常量表中（`x-client-name / x-client-platform / x-client-version / x-client-os-version / x-client-channel / x-client-device-id`）。字段来自 `ClientInfo` dataclass（`from_meta` 从 meta 字典读 alias）。

| Header | Python 端字段 | 实际值来源（Electron 注入） | 真实线上值 | 是否可变 |
|---|---|---|---|---|
| `x-client-name` | `name` | `readOfficePackageName()`，读 package.json `name` 字段，兜底 `app.getName()` → `'raccoon-ai'` | `raccoon-ai` | 可被 meta 覆盖 |
| `x-client-platform` | `platform` | `normalizeDesktopPlatform(process.platform, process.arch)`，规则见下 | `desktop-windows-x64`（注意：**带架构**） | 可被 meta 覆盖 |
| `x-client-version` | `version` | `normalizeClientVersion(app.getVersion())`，**强制加 `v` 前缀** | `v1.0.35` | 可被 meta 覆盖 |
| `x-client-os-version` | `os_version` | `readSystemVersion()` = `process.getSystemVersion()` 兜底 `os.release()` | `10.0.26200` | 可被 meta 覆盖 |
| `x-client-channel` | `channel` | 常量 `BOX_AGENT_CLIENT_CHANNEL` | `official` | 常量 |
| `x-client-device-id` | `device_id` | `desktop-device-identity.json` 的 `clientDeviceId` | `4e43f8ed-af82-471d-ba09-b2f78b096f63`（样本） | 每安装一次随机 |

**关键细节（与受信设备头区分）**：
- box-agent 的 `platform` 是 `desktop-{os}-{arch}`（**带架构**，如 `desktop-windows-x64`），证据 `boxAgentManager.js:107-118` `normalizeDesktopPlatform`。
- 而受信设备 HTTP 头 `X-Client-Platform` 用的是 `resolveDesktopClientPlatform`（`desktopDeviceIdentity.js:16-27`），是 `desktop-windows`（**不带架构**）。两套 platform 格式不同，是两条独立链路。
- box-agent 的 `version` 带 `v` 前缀（`normalizeClientVersion`，`boxAgentManager.js:101-106`：`startsWith('v') ? v : \`v${v}\``）。Python 端 `headers_for_url` 还会用正则 `v?(0|[1-9]\d*)\.(0|[1-9]\d*)\.(0|[1-9]\d*)` 校验并 `removeprefix('v')`，所以**发到服务端的是不带 v 的 `1.0.35`**（version 一旦不符合 semver 会被置 `'unknown'`）。

### 1.3 清洗规则 `_clean_header_value`（client_info.pyc）
- 非 str → 强转 str；
- `strip()`；
- 去除所有控制字符（genexpr 常量 `(32, 127)`，逻辑：`ord(c)` 不在 [32,127) 可打印区间即剔除）；
- 非 ASCII（`isascii()` 为 False）→ 整体置 `''`；
- 超过 `_MAX_HEADER_VALUE_LENGTH = 256` 截断到 256。
结论：**只保留 ASCII 可打印字符，≤256 字节**。

### 1.4 额外的关联头（彩蛋，常被忽视）
`pyz/modules/box_agent/llm/base.pyc` → `LLMClientBase._agent_headers` 每个 LLM 请求还带：
- `X-RACCOON-Session-ID`、`X-RACCOON-Turn-ID`、`X-RACCOON-Title`、`X-RACCOON-Call-Kind`

这四个头是**会话级关联标识**，`_request_headers`（consts: `'Return correlation plus host client headers for one request.'`）把它们和 x-client-* 合并发出。反代若复刻客户端，需要决定是复刻（维持服务端会话追踪）还是置空（降低关联）。

## 2. 设备指纹生成机制

### 2.1 clientDeviceId：**随机 UUID，非硬件派生**
证据 `desktopDeviceIdentity.js`（`remote/connectors/mobile/device/desktopDeviceIdentity.js`）：

```
L13:  const IDENTITY_FILE_NAME = 'desktop-device-identity.json';
L64:  this.randomUUID = options.randomUUID || node_crypto_1.randomUUID;
L90-95: 若无持久化 → persisted = {
           schemaVersion: 1,
           clientDeviceId: this.randomUUID(),   // ← crypto.randomUUID()，纯随机 v4
           createdAt: this.now().toISOString(),
         }
```

样本文件 `C:\Users\HUIDADA\AppData\Roaming\office-raccoon\desktop-device-identity.json`：
```json
{ "schemaVersion": 1,
  "clientDeviceId": "4e43f8ed-af82-471d-ba09-b2f78b096f63",
  "createdAt": "2026-09-15T08:33:34.994Z" }
```

**完全没有取 MAC / 主板序列号 / CPU ID / 机器 GUID**。`node_crypto.randomUUID()` 就是 RFC4122 v4。

### 2.2 持久化与安全
- 写入用临时文件 + `rename` 原子替换，权限 `0o600`（L96-101）。
- 读取时若 JSON 非法，会把旧文件改名 `*.corrupt-{timestamp}` 后重新生成（L82-89）。
- 校验 `isValidPersistedIdentity` 只查 `schemaVersion===1 && clientDeviceId 是非空字符串 && createdAt 是字符串`（L111-119）。**不校验 UUID 格式**，所以反代可以写任意非空字符串当 device id（但建议仍用合法 UUID，避免服务端格式校验）。

### 2.3 删除/更换的影响
- 删除该 JSON → 下次启动生成**全新随机 UUID** → 对新设备走 `devices_current_bind` 重新绑定，服务端会登记一台"新设备"。
- 更换为固定值 → 应用把它当稳定设备用，心跳/绑定全用这个 id。
- **服务端是否对单账号设备数/设备更换频率有限制：未确认/需抓包验证**（客户端代码里没有任何关于上限的处理逻辑，只有 `device_session_mismatch` 一个错误码）。

### 2.4 渲染层 fingerprintjs：**无实质采集**
对 `desktop-renderer/_next/static/chunks/` 全部 chunk 搜索 `fingerprintjs / visitorId / FingerprintJS / fpjs / getFingerprint`，命中的 "fingerprint" 全部为：
1. 代码编辑器语法高亮定义里的 PGP/Lisp 关键字 (`b74732b4.js`：`pg-...-fingerprint`、`sm-fingerprint`)；
2. 一个 FNV-1a 文本 hash 工具 (`82749-*.js`：`t=0x811c9dc5; ... t=Math.imul(t,0x1000193)`)，用于给会话消息内容算去重指纹，**不发网络**。

结论：**渲染层无浏览器指纹采集与上报**。会话 0 总纲里"machine_id 来自 @fingerprintjs"那条是误判，实际是硬编码常量（见 §5）。

## 3. 受信设备绑定全流程

### 3.1 触发与状态机（`desktopTrustedDeviceManager.js`）
Manager 状态：`stopped → waiting_for_context → (binding →) trusted / degraded / device_mismatch / authentication_required / error / waiting_for_trusted_device`

时序（文字版）：
1. `updateContext({sessionId, needsBind, trusted})` 由登录态/移动接入触发（`remote/connectors/mobile/device/index.js:56` `desktopTrustedDevice.syncContext`）。
2. `needsBind === true` → 状态 `binding`，调 `bindWithOneRefresh` → `POST /devices_current_bind`；401 则刷新 token 后重试**一次**（`bindWithOneRefresh`，行 153-164）。
3. 绑定/已受信 → 进入 `runHeartbeat`：若是续接（`refreshDeviceMetadata=true`）会**先补一次 bind 刷新元数据**，再发心跳。
4. 心跳成功 → 状态 `trusted`，记录 `lastHeartbeatAt`，然后 `setTimeout(下一次, heartbeatIntervalMs ?? 60000)`（行 232-241）。**心跳间隔 = 60s**（构造时未传 `heartbeatIntervalMs`，`index.js:33-41` 只传了 auth/getIdentity/api 三个 dep，所以走默认值 60000ms）。
5. 任意失败（非终态）→ 状态 `degraded`，**仍按 60s 重试**（`scheduleHeartbeat`），不会因失败而指数退避。
6. 终态错误分类（`isTerminalError`，行 292-297）：
   - 401 / `authentication required` → `authentication_required`（提示重新登录，停心跳）
   - `device_session_mismatch`（`isDeviceMismatch`，行 286-288）→ `device_mismatch`（停）
   - 其他 → `degraded` 继续重试

### 3.2 绑定请求精确格式（`desktopTrustedDeviceApi.js`）
- `POST {base}/api/web/auth/v1/devices_current_bind`
- 请求头（L88-95）：
  - `Authorization: Bearer <access_token>`
  - `Content-Type: application/json`
  - `X-Client-Platform: desktop-windows`（无架构，来自 `buildDesktopDeviceMetadata`）
  - `X-Client-Device-ID: <clientDeviceId>`
  - `X-Client-Version: 1.0.35`（无 v 前缀）
  - `X-Request-Id: <uuid4>`（每次请求新生成）
- 请求体（L61-71，键名蛇形）：
```json
{
  "client_device_id_source": "unknown",
  "client_device_id":   "<clientDeviceId>",
  "client_platform":    "desktop-windows",
  "client_version":     "1.0.35",
  "device_name":        "<hostname 经 sanitize>",
  "os":                 "windows",
  "os_version":         "<os.release()>",
  "application":        "desktop",
  "push_permission":    "unknown"
}
```
- `client_device_id_source` 与 `push_permission` 是**硬编码 `unknown`**。spec（`desktopTrustedDeviceApi.spec.js:95`）显示服务端 details 会回 `param client_device_id_source invalid`，但客户端把它当可接受（仅作为脱敏诊断字段），说明服务端对该值**宽容**。
- `device_name` 清洗（`desktopDeviceIdentity.js:40-46`）：去控制字符→压空白→trim→截 120 字符，空则 `'Desktop'`。
- 成功返回：`{code:0, data:{device_id:"<服务端ID>"}}`，客户端只取 `device_id` 字符串（L73-79），**不持久化**（未发现落盘，session 内存里）。

### 3.3 心跳请求
- `POST {base}/api/web/auth/v1/devices_current_heartbeat`，**无请求体**（`heartbeat()` 不调 body，`desktopTrustedDeviceApi.js:81-83`），只带与 bind 相同的五个头（含新 `X-Request-Id`）。
- 401 → `heartbeatWithOneRefresh` 刷新 token 重试一次（行 220-231）。
- 心跳返回体未被解析（fire-and-forget，仅判 HTTP ok + code==='0'）。

### 3.4 设备数上限迹象
**未发现客户端侧任何上限处理逻辑**。唯一相关错误码是 `device_session_mismatch`（语义：当前 token 对应的登录会话与该设备登记的会话不一致，典型场景：同一账号在另一台设备登录把本机顶掉）。
单账号可绑几台、超限错误码是什么：**未确认/需抓包验证**。建议反代投产前用真实账号实测"同一 token 从不同 device_id 发 bind"的服务端响应。

## 4. 防伪隐藏层排查结论

对以下做了全文搜索+反汇编确认，**全部没有**：

| 机制 | 结论 | 证据 |
|---|---|---|
| 请求签名 / HMAC | **无** | `grep createHmac/Hmac/`sign` 在 device 目录、boxAgentManager、desktopAnalytics 均 0 命中（device 目录命中的全是变量名 `signal`） |
| nonce / X-Sign / X-Timestamp | **无** | 同上 grep；Python 端 strings 无 `nonce`/`signature`/`timestamp`（除 `X-Request-Id`，仅 UUID，不参与签名） |
| 防重放 | **无** | 无 timestamp/nonce 字段，重放旧请求只靠 token exp（3h）自然过期 |
| 证书 pinning | **无** | 桌面端用系统/Node fetch，无自定义 CA 校验代码 |
| 代码混淆 | **无** | Electron asar 解包即可读编译后 tsc 输出；Python 端 PyInstaller marshal 可直接 dis |
| 反调试 | **无** | 未见 debugger 检测/完整性校验 |

**JWT 是唯一真凭证**（HS256，3h access + 30d refresh），见 `auth.pyc`：`refresh_token` 走 `POST /api/web/auth/v1/refresh`，刷新窗口 `AUTH_REFRESH_WINDOW_SECONDS = 300`。token 拿到手即可在南京/任何机器上直接用，没有绑定首次签发设备的二次校验（设备绑定是**独立的旁路校验**，不签名进 token）。

## 5. 遥测上报与多账号关联风险

### 5.1 桌面主进程遥测（`desktopAnalytics.js`）
- 端点：`POST {origin}/{/api/web | /api/web/org}/b/v1/m`（个人/团队分流，行 36-42）
- 头：`Authorization` + `X-Org-Code`（团队）+ `Content-Type`
- body `common_header`（行 60-64）：
```json
{ "client_agent": "<userAgent 截 1024>",
  "machine_id": "simulator-f31d2afc795804bbff66711fdc50fd44228798698e70438c70d4ba1501b248b8" }
```
- **`machine_id` 是文件顶部硬编码常量 `ACTIVITY_MACHINE_ID`（L6），所有客户端完全一样**，不构成区分。
- 只发一个固定 `activity` 事件（id=1），prompt 字段塞 `Date.now()`（毫秒时间戳）。

### 5.2 渲染层遥测（`75741-*.js`）
同样硬编码同一个 `machine_id: simulator-f31d...`，`client_agent: navigator.userAgent` 兜底同一个固定 UA 串。额外支持按白名单 `c.q.includes(e)` 上报自定义事件。**同样无设备区分能力**。

### 5.3 UA
`DEFAULT_USER_AGENT = 'Mozilla/5.0 (X11; Ubuntu; Linux x86_64; rv:136.0) Gecko/20100101 Firefox/136.0'`（Linux/Firefox UA，明显是占位数——真实 Windows 桌面端应该传真实 UA 或这个占位串。**反代时应统一用真实桌面 UA 池，不要所有号都用同一个 simulator UA**，否则 simulator UA 本身会成为群控特征）。

### 5.4 关联泄露面汇总
| 维度 | 是否暴露同源 | 说明 |
|---|---|---|
| `machine_id` | 否 | 全局硬编码常量 |
| `x-client-device-id` | **是** | 随机 UUID，同机同号固定；多号共用一台裸机会暴露 |
| `client_agent` / UA | 部分 | 若全用默认 simulator UA → 群控特征 |
| 出口 IP | **是** | 网络层，客户端代码改不了 |
| `X-Request-Id` | 弱 | 每次请求随机 UUID，无时序泄露 |
| 心跳时序（60s 准点） | **是** | 同机多号心跳若同相会有聚类特征 |
| `X-RACCOON-Session/Turn-ID` | 中 | 会话粒度关联，跨号不复用即可 |

## 6. 号池指纹隔离方案（每个号一套独立指纹）

设计目标：**让每个号在服务端视角是一个独立的、长期稳定的、行为自然的"设备+人"**。

### 6.1 每号独立身份画像（必须随机化且持久化的字段）

| 字段 | 反代取值 | 生成规则（不被识别为伪造的关键） |
|---|---|---|
| `x-client-device-id` / bind 的 `client_device_id` | 每号一个随机 UUID v4，**绑定后固定不变** | `crypto.randomUUID()`，存进号池 DB（如 `{account_id: {device_id, device_name, os_version, ua}}`）。**不要每次请求变**（变化本身是风控信号） |
| `x-client-platform` | 每号从 `desktop-windows-x64 / desktop-macos-arm64 / desktop-windows-arm64` 中选一个并固定 | 与 UA 的 OS 必须一致；真人 Windows x64 占绝大多数，建议 90% 分配 `desktop-windows-x64` 贴近自然分布 |
| `x-client-version` | 固定 `1.0.35`（跟随当前最新版） | 所有号同版本是自然的（自动更新），不要伪造五花八门版本号 |
| `x-client-os-version` | 每号从真实 Windows build 池采：`10.0.26200 / 10.0.26100 / 10.0.22631 / 10.0.19045` | 与 platform 对应；mac 号用 `23.x / 24.x` darwin 版本 |
| `x-client-channel` | 永远 `official` | 常量，无自由度 |
| `x-client-name` | 永远 `raccoon-ai` | 常量 |
| `device_name`（bind body） | 每号一个拟真主机名：`DESKTOP-XXXXXX`/`沪A-PC-01`/`MacBook-Pro-3.local` | Windows 默认是 `DESKTOP-` + 7 位大写字母数字；切莫用 `simulator`/`test`/`raccoon` 等字样 |
| `os` | 与 platform 一致：`windows`/`macos` | |
| 心跳 `X-Request-Id` | 每次心跳新生成 UUID v4（与官方一致） | 无需特殊处理 |

### 6.2 时序隔离（防时序聚类）
- 心跳 60s 是硬约定，但**起始相位必须错开**：第 i 个号初始延迟 `random(0..60s)`，之后固定每 60s；再加 ±5s 抖动（官方 Manager 用 setTimeout 天然有毫秒级抖动，±5s 不会异常）。
- 不要让 N 个号在同一秒齐发心跳（这是号池最经典的死法）。

### 6.3 网络层隔离
- 出口 IP 是唯一无法靠改字段解决的维度。**建议每号配一独立出口（代理/软路由）**，至少做到"同 IP 同时在线号数 ≤ 3"。
- x-client-device-id 隔离了，但你 IP 没隔离，风控仍能把同 IP 的号聚类后人工/离线核查行为；两者必须同时做。

### 6.4 遥测层降噪
- 反代**不需要也不应该**复刻官方遥测上报（`/b/v1/m`）。官方遥测只发一个固定 activity 心跳事件，不发基本不会被风控盯（这是活跃度统计，不是风控）。若担心"长时间无 activity 事件"异常，可按低频率（如每重启一次发 1 条）补发。
- 若补发，`client_agent` 用该号 UA，`machine_id` 保留官方硬编码常量（它就是所有客户端共用的，不要改成随机值——改了反而成唯一特征）。

### 6.5 登录/刷新层
- 每个号的 `auth.json`（access+refresh token）独立，互不复用（oken 本身天然隔离）。
- 刷新走 `/api/web/auth/v1/refresh`，刷新时也带 x-client-* 头（Python `auth.pyc` 走同一 `bearer_auth_headers` + client_info 注入链），所以刷新请求也必须用该号的指纹，不能混。

### 6.6 不要做的事
- **不要**在 device_id 里编码日期/序号/IP 等信息（如 `dev-20260921-001`）——服务端做格式/熵分析时这是明显伪造特征。
- **不要**让同一号在中途更换 device_id（换机是罕见事件，频繁换 = 风控）。
- **不要**所有号统一 `os_version=10.0.26200`——太齐整；按真实 Win11 各 build 分布抽样。
- **不要**伪造 fingerprintjs/visitorId 之类（官方根本没有这层，多此一举反而留下不一致证据）。

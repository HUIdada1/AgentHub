# 会话4 · 积分 / 余额 / 配额查询 —— 独立审查报告

> 审查范围：商汤小浣熊（Raccoon AI）桌面端的**积分余额、积分明细、账户配额、套餐/订阅状态、登录送积分**。
> 逆向对象：渲染层 chunk `desktop-renderer/_next/static/chunks/*.js`（未混淆、可读），主进程 `electron/main/*.js`，Python `box-agent`。
> 结论先行：**积分与配额的查询全部发生在渲染层（renderer）**，Electron 主进程与 box-agent 均不参与（主进程仅 LLM 转发与设备绑定，box-agent 仅推理）。所有接口走统一的 `fetchWithAuth` 信封 `{code, data}`，鉴权为 `Authorization: Bearer <access_token>`。

### 0.1 host 构造函数（模块 79746，chunk `75741-e691f872602fccb9.js`）

> 注意：`hj()` 内部对 office 子域做了一层 `(0,i.Ri)("office_home")` 覆盖，反代时直接用主域名 `https://xiaohuanxiong.com` 即可。

### 0.2 统一请求基类 `fetchWithAuth`（类 `A`，chunk `75741`，索引 ~285776）
- 每次请求先 `refreshTokenIfNeeded()`：`exp - now <= 300s` 时自动调 `POST /api/web/auth/v1/refresh`；桌面端优先走 `window.electronAPI.desktopAuth.ensureAccessTokenReady()`。
- 默认超时 60s；401 且 token 变化自动重试一次。
- **返回值 = `response.json()` 整体**，即 `{code:0, data:...}`；各 SDK 方法再 `.data` 取业务字段。
- 请求头（`createHeaders()`）：`Content-Type: application/json`、`Authorization: Bearer`、`X-Org-Code`（团队）、`X-Raccoon-Language`、桌面端另有 `X-Client-Platform`/`X-Client-Version`/`X-Client-Device-ID`。

| （通用 reward） | — | `有效期至 {date}（发放时刻起1年）` |

### 7.5 薅积分结论
- **可薅**：每日登录桌面端 → grant 接口发放每日积分（免费 300/日，pro 500/日）。号池批量账号每日各调一次 grant 即可领满每日额度。
- 每日积分**默认当日 24:00 清零**，但**当天登录后延长至 7 天**——即每日必须登录一次才能锁定。
- 每月额度仅 pro，新订阅周期首次登录自动到账。
- 积分到账也会通过 `setting_info` 响应的 `point_grant_popups` 推送。

## 8. 积分体系规则（i18n FAQ 实证，chunk 75741 `settingModal.resource.points.faq`）

1. **积分 = 算力计量单位**。每次 AI 对话/执行任务消耗积分，任务越复杂消耗越多。
2. **消耗顺序（先到期先用）**：`每日额度 → 每月额度 → 奖励积分 → 加油包`，同类内按到期日/入账时间排序。
   - 对应 UI 文案 `consumptionOrder` 实证。
3. **加油包永久有效**，但退订回免费版会**冻结**（`topup_frozen`），续订后恢复。
4. **明细只保留 3 个月**，有几分钟同步延迟。

## 9. 余额/配额查询接入号池的方案

### 9.1 号池"余额页"数据结构（每账号一行）
```ts
interface AccountBalance {
  accountId: string;            // 号池内部 ID（= user_info.id）
  name: string;                 // user_info.name
  // 套餐
  isPro: boolean;               // entitlement_info.office.pro_enable
  planLabel: "free"|"personal-pro"|"education"|"alipay"|"unavailable";
  subscriptionExpiredAt?: string;
  autoRenew?: boolean;
  isUniversityApplied?: boolean;// user_info.is_office_university_applied
  // 积分（来自 /balance）
  availablePoints: number;      // 总可用余额 ← 号池排序主键
  dailyPoints: number;
  monthlyPoints: number;
  rewardPoints: number;
  topupPoints: number;
  topupFrozen: boolean;
  // 配额（来自 setting_info）
  dailyQuestion: { used: number; limit: number };   // daily_question_count/limit
  webSearch: { used: number; limit: number; period: "day"|"month" }; // pro=monthly 否则 daily
  storageMb: { used: number; total: number };
  knowledgeMb: { used: number; total: number };
  // 状态
  quotaExhausted: boolean;      // daily_question_count>=limit || 联网超限
  fetchedAt: number;            // 缓存时间戳
}
```

### 9.2 单账号采集流程（每账号 3 个 GET + 1 个 POST）
```
1. POST /api/web/desktop/v1/login/points/grant   （先薅当日积分，幂等，granted=true 才变了余额）
2. GET  /api/web/points/v1/balance                （余额 6 字段）
3. GET  /api/web/office/v3/setting_info           （配额 + available_points 冗余 + point_grant_popups）
4. GET  /api/web/auth/v1/entitlement_info         （套餐 pro_enable / 订阅状态）
   （可选）GET /api/web/auth/v1/user_info          （大学认证 / orgs / 姓名）
```
> 全部带 `Authorization: Bearer` + `X-Client-Platform/Version/Device-ID`。访问令牌 3h、刷新窗口 300s，采集前先走 `refresh`。

### 9.3 批量轮询 / 缓存建议
- **余额**：积分变动只在对话/任务后发生，轮询间隔 **5~10 分钟**足够；触发式刷新（本账号跑完一次任务后立即刷一次）更省。
- **配额**：`daily_question_count` 每次对话都变，建议**每次任务后刷新**；`setting_info` 与 `entitlement_info` 可合并为一次"账号状态"轮询，间隔 10~15 分钟。
- **grant 签到**：每日 00:00 后首次采集时调一次即可，用 `granted` 判断避免无效请求；做个"今日已签到"标记，跨天重置。
- **缓存**：`available_points` 与配额写 Redis/hash，TTL=轮询间隔；`setting_info` 同时是弹窗载体，注意剥离 `point_grant_popups` 再入库。
- **并发**：逐账号串行或低并发（≤4），每账号 4 个请求约 4×RTT；541 个 chunk 无证据显示有频控，但保守起见账号间错开。

### 9.4 号池展示优先级
1. 列表排序键：`availablePoints`（降序）+ `quotaExhausted`（置底）。
2. 高亮告警：`quotaExhausted`、`topupFrozen`、`subscriptionExpiredAt` 临近、存储 ≥90%。
3. 明细页（点击展开）：调 `/bills?type=all&paging.limit=20` 游标翻页，渲染 `event_name||biz_type` / `points` / `created_at`，桌面会话按 `biz_id` 前缀聚合。

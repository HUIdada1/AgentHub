# 会话 5 —— 号池风控与多账号反关联审查报告

> 独立审查会话 5/6。只回答一件事：**把小浣熊多个账号接入 AgentHub 号池、在同一台机器/同一出口 IP 下轮换调用，如何不被服务端关联批量封。**
>
> 依据：`docs\raccoon-反代\00-总纲-背景事实.md` + 本会话对 Electron 主进程与 box-agent Python 模块的二次深挖。全文严格区分【实证】（代码里看得见）与【推测】（由实证合理外推）。

---

## 0. 一句话结论（先给答案）

小浣熊的客户端防伪体系是**"JWT + 受信设备绑定 + 60s 心跳 + 客户端指纹头 + 遥测"**五件套，其中 **clientDeviceId（设备指纹）和受信设备绑定是会暴露"同机"的最强信号**，必须做到**每号一份独立 clientDeviceId + 独立 device 绑定 + 独立心跳**；IP、UA、OS 版本是次级信号，建议每号独立出口 IP 池 + UA/版本错开。只要这五件套不"同源"，单号被风控不会连坐整池。

## 1. 关联风险点枚举与评级

下表枚举"多账号共用同一台机器"时可能暴露"同源"的全部字段，逐个标注是否同源可见与风险等级。

### 1.1 关联风险点清单表

| # | 字段 | 载体 / 证据 | 是否同源可见 | 风险等级 | 缓解措施 |
|---|------|------------|------------|---------|---------|
| 1 | **出口 IP** | 所有 HTTPS 请求 | 同机同网必然相同 | **高**（多号同 IP + 高并发 = 最经典关联特征） | 每号独立代理/出口 IP 池，轮换时切 IP |
| 2 | **clientDeviceId** | `x-client-device-id` 头 + devices_current_bind body + machine_id | **同机默认全相同**（读同一 `desktop-device-identity.json`）【实证 desktopDeviceIdentity.js:63,92-101】 | **极高** | 每号独立 identity 文件/独立 clientDeviceId |
| 3 | **受信设备绑定 device_id** | `devices_current_bind` 返回的服务端 device_id | 同 clientDeviceId 绑出同一 device_id【实证 desktopTrustedDeviceApi.js:59-80】 | **极高** | 每号独立 bind，不复用 |
| 4 | **心跳 fingerprint** | `devices_current_heartbeat` 每 60s 一次 | 同机同频率、同 clientDeviceId【实证 desktopTrustedDeviceManager.js:151,240】 | **高** | 每号独立心跳循环，相位错开 |
| 5 | **遥测 machine_id** | `common_header.machine_id`（skillHub 上报用 clientDeviceId；desktopAnalytics 用固定常量） | skillHub 用 clientDeviceId【实证 skillHubManager.js:281-296】；desktopAnalytics 用固定常量【实证 desktopAnalytics.js:6】 | **中高** | 池化时关闭 skillHub 使用上报，或每号独立 machine_id |
| 6 | **遥测 client_agent / UA** | `common_header.client_agent` | skillHub 默认 `Raccoon Desktop Electron/<ver> (win32; x64)`【实证 skillHubManager.js:288-289】 | 中 | 池化时关闭遥测，或 UA 错开 |
| 7 | **x-client-*** 指纹头 | `x-client-name/platform/version/os-version/channel` | 全部相同（同机同版本）【实证 client_info.dis.txt `headers_for_url`】 | 中 | 每号错开 version/os_version/channel |
| 8 | **os_version / os release** | `x-client-os-version` = `os.release()` | 同机相同 | 低-中 | 虚拟化成不同 Windows build 号 |
| 9 | **client_version (1.0.35)** | `x-client-version` | 相同 | 低 | 可错开（1.0.33~1.0.35） |
| 10 | **device_name / hostname** | `devices_current_bind` body.device_name | 同机相同【实证 desktopDeviceIdentity.js:40-55】 | 中 | 每号随机 hostname |
| 11 | **JWT sid / jti** | access_token payload | 每号独立 | 无（天然隔离） | — |
| 12 | **refresh_token** | auth.json | 每号独立 | 无 | 每号独立 auth.json |
| 13 | **刷新时间窗口** | AUTH_REFRESH_WINDOW_SECONDS=300【实证 auth2.dis.txt:105 `LOAD_CONST 13 (300)` / auth.py:30】 | 同机多号会在相近时刻刷新 | 低 | 刷新相位加抖动 |
| 14 | **积分 grant / 配额字段** | `login/points/grant` + `daily_question_count/limit` 等 | 每号独立计数 | 无（这是服务端给每号的额度，不是关联信号） | 用作健康度巡检探针 |

### 1.2 风险等级判定逻辑

- **极高（连坐元凶）**：clientDeviceId、受信 device_id —— 这两个是服务端"设备表"的主键，一旦多号共用同值，服务端 `GROUP BY device_id` 就能看到"这台设备挂了 N 个号"，批量封只需一条 SQL。
- **高**：出口 IP、心跳指纹 —— IP 是网络层最强关联特征；心跳暴露"这台设备 24h 在线"。
- **中**：遥测 machine_id/client_agent、指纹头、device_name —— 辅助画像，用于给"可疑设备"打分。
- **低**：os_version、client_version、刷新窗口 —— 弱信号，单独不构成关联。

> 【推测】风控工程师真正写规则时，几乎一定是 `device_id` + `IP` 做硬关联、其余做软打分。所以**优先级：独立 clientDeviceId/device 绑定 > 独立 IP > 关遥测 > 错开指纹头**。

## 2. 服务端风控维度推断（实证 / 推测分离）

### 2.1 代码实证（客户端代码直接可见的行为）

| 维度 | 实证内容 | 证据 |
|------|---------|------|
| **受信设备绑定是强制环节** | 登录后必须 `devices_current_bind` 拿 device_id，绑定失败会自动 refresh 重试一次（`bindWithOneRefresh`） | desktopTrustedDeviceManager.js:153-164；desktopTrustedDeviceApi.js:59-80 |
| **心跳是持续保活** | 默认 60s 一次 `devices_current_heartbeat`，失败进 `degraded` 状态并自动重试 | desktopTrustedDeviceManager.js:151,165-241 |
| **设备不匹配会触发专属错误** | 服务端返回 `code='device_session_mismatch'` 时客户端进入 `device_mismatch` 终态 | desktopTrustedDeviceManager.js:192-200,286-288 |
| **token 过期会被识别** | 401 → `authentication_required`，提示"登录态已失效，请重新登录" | desktopTrustedDeviceManager.js:201-211,255-263 |
| **刷新有窗口期** | `AUTH_REFRESH_WINDOW_SECONDS=300`，exp 前 300s 内才刷新 | auth.py:30 / auth2.dis.txt:105 |
| **refresh 失败兜底** | 刷新 401 → `HostedAuthRequiredError("登录态已过期，请重新登录")`；其他 HTTP 错误在 token 未过期时静默沿用旧 token | auth.py:246,265-269 / auth2.dis.txt:1297-1330 |
| **遥测有独立通道** | `POST /api/web/b/v1/m`（个人）/ `/api/web/org/b/v1/m`（团队），body 含 `common_header:{client_agent, machine_id}` | desktopAnalytics.js:39-78；skillHubManager.js:290-311 |
| **积分登录赠送** | `POST /api/web/desktop/v1/login/points/grant`，每次登录调用 | 渲染层 chunk 75741：`.grantDesktopLoginPoints` |
| **配额有服务端计数** | `daily_question_count/limit`、`monthly_web_search_count/limit`、`used_space_mb` 等字段 | 渲染层 chunk 75741 |

### 2.2 由实证合理外推的推测（标注【推测】）

| 维度 | 推测内容 | 依据 |
|------|---------|------|
| **单设备多号上限** | 【推测】服务端大概率对"同一 device_id 绑定账号数"设上限（如 3~5 个）。客户端有 `device_session_mismatch` 错误码，说明服务端有"设备-会话"映射表，这个表天然可做 N:1 限制。 | 由 device_session_mismatch 错误码的存在外推 |
| **同设备多号检测** | 【推测】服务端会统计 `device_id` 关联的不同 `owner_type/sid`，超过阈值打"养号/号池"标签。 | 设备表设计的标准用法 |
| **异常调用检测** | 【推测】基于 `daily_question_count` 配额 + token usage 计费，服务端能识别"短时高频刷题""24h 不间断调用"等非人行为。心跳保活 60s 意味着"设备离线即停止计费"，长时间在线本身就是信号。 | 配额字段 + 心跳机制 |
| **IP 聚集检测** | 【推测】同 IP 多账号 + 高 QPS 会触发 WAF/风控限流（429），但小浣熊主站是普通 SaaS，IP 风控强度中等。 | 行业标准做法 |
| **登录地点/设备突变** | 【推测】同一账号短时间从"设备 A"切到"设备 B"（不同 clientDeviceId）会触发二次验证或重新绑定。 | devices_current_bind 的存在说明服务端关心"当前设备" |
| **遥测画像** | 【推测】`machine_id` + `client_agent` 用于构建设备画像，但 desktopAnalytics 的 `ACTIVITY_MACHINE_ID` 是**写死的常量** `simulator-f31d...`（desktopAnalytics.js:6），说明这条通道目前更像"占位/调试"而非严格风控。 | 常量化的 machine_id |

> **结论**：【实证】服务端**一定有**设备绑定表和心跳在线状态；【推测】它**很可能**用设备表做多号聚集检测，用配额+心跳做异常调用检测。**最该防的是"同 device_id 挂多号"，其次是"同 IP 高并发"。**

## 3. 每号独立指纹完整方案（隔离粒度建议）

### 3.1 隔离粒度决策表

| 指纹项 | 是否每号独立 | 隔离方式 | 理由 |
|--------|------------|---------|------|
| **clientDeviceId** | ✅ 必须独立 | 每号一份独立 identity 文件（独立 UUID） | 服务端设备表主键，共用=直接连坐 |
| **受信 device_id（bind）** | ✅ 必须独立 | 每号独立调 `devices_current_bind`，不复用 device_id | 绑定关系是服务端关联锚点 |
| **心跳** | ✅ 必须独立 | 每号独立 60s 心跳循环，相位随机抖动 ±15s | 同机同频率心跳=同源铁证 |
| **auth.json（token）** | ✅ 必须独立 | 每号独立 auth.json 路径（`~/.box-agent/config/auth-<accountId>.json`） | token 本来就是每号的 |
| **遥测 machine_id** | ✅ 独立或关闭 | 池化模式下**建议关闭** skillHub/desktopAnalytics 上报；必须上报时每号独立 machine_id | 遥测是免费画像数据源 |
| **出口 IP** | ✅ 强烈建议独立 | 每号绑定一个代理出口，轮换时连 IP 一起换 | 网络层最强关联特征 |
| **UA / client_agent** | 🟡 建议错开 | 每号从 UA 池随机取（Electron 版本/平台变体） | 辅助画像，错开降低画像一致性 |
| **x-client-version** | 🟡 建议错开 | 在 1.0.33~1.0.35 间随机 | 版本聚齐本身不违规，但全相同可疑 |
| **os_version / device_name** | 🟡 建议错开 | 虚拟化成不同 Windows build 号、随机 hostname | 辅助画像 |
| **x-client-channel** | ❌ 保持 `official` | 常量，改了反而异常 | 【实证 boxAgentManager.js:99】`BOX_AGENT_CLIENT_CHANNEL='official'`，非 official 才是异类 |
| **x-client-name** | ❌ 保持 `raccoon-ai` | 常量 | 【实证 client_info.dis.txt】默认 `raccoon-ai` |

### 3.2 具体实现要点

**每号独立 clientDeviceId 的落地方案**（这是最关键的一条）：

官方逻辑是读 `userDataPath/desktop-device-identity.json`，没有就 `randomUUID()` 生成一个并持久化【实证 desktopDeviceIdentity.js:71-102】。号池方案：

- **方案 A（推荐）**：每号一个独立 `userDataPath`（或多实例隔离的 identity 文件），让每号自然长出不同 clientDeviceId。AgentHub 号池里给每个账号存一个 `identity: { clientDeviceId, deviceName, osVersion, clientVersion }`，首次入池时生成并固定。
- **方案 B**：如果走自研反代（不跑官方 Electron），直接在请求层给每号注入不同的 `x-client-device-id` 头 + `devices_current_bind` body 里的 `client_device_id`。box-agent 的 `ClientInfo.from_meta` 接受外部 meta 注入 `device_id`【实证 client_info.dis.txt `from_meta` line 61-82】，号池在调 box-agent 时传每号独立的 meta 即可。

**每号独立心跳**：

- 心跳间隔 60s 是客户端默认值【实证 desktopTrustedDeviceManager.js:151,240 `heartbeatIntervalMs ?? 60000`】。
- 号池里每号起一个心跳定时器，但**相位加随机抖动**（如 60s ± 15s），避免 N 个号在同一秒齐刷刷发心跳（齐发本身就是"同机调度"特征）。
- 心跳失败处理沿用官方语义：401 → 标记 `authentication_required`；`device_session_mismatch` → 标记 `device_mismatch` 并换号【实证 desktopTrustedDeviceManager.js:192-211】。

**遥测处理**：

- desktopAnalytics 的 machine_id 是写死的常量【实证 desktopAnalytics.js:6】，这条通道威胁小，但**还是建议池化模式整个关掉**（不发 `/api/web/b/v1/m`），少一个数据源少一分画像。
- skillHub 使用上报会用真实 clientDeviceId 当 machine_id【实证 skillHubManager.js:281-296】，**必须关**——否则每号每用一次 skill 就上报一次设备 ID，等于主动告诉服务端"这台设备在用这个号"。

## 4. IP / 出口策略与调用节奏

### 4.1 多号同 IP 风险

- 【实证】所有请求走 HTTPS 到 `xiaohuanxiong.com`，无证书 pinning、无请求签名【00-总纲】，网络层只剩 IP 这一个关联维度。
- 【推测】同 IP + 多号 + 高并发 = 风控教科书式的"号池/工作室"特征。**这是仅次于 clientDeviceId 的第二大关联源。**

### 4.2 出口策略建议

| 策略 | 建议 |
|------|------|
| **代理池** | 号池规模 > 3 号时**必须**配代理池。每号绑定一个独享 IP（住宅代理优于机房代理），轮换账号时连代理一起切。 |
| **IP 与账号绑定** | 一个号长期固定一个 IP 比"每次随机 IP"更像真人（真人家里 IP 相对稳定）。建议"号-IP"一对一绑定，只在 IP 失效时换。 |
| **降级方案** | 实在没代理池，至少把并发压到极低（见 4.3），并接受"同 IP 多号"的残余风险——此时 clientDeviceId 独立就更不能省。 |

### 4.3 调用节奏（QPS / 并发 / 日限额）建议

> 【推测为主，配额字段实证】小浣熊是带积分/配额体系的 SaaS，不是免费无限接口，节奏建议偏保守。

| 维度 | 建议值 | 依据 |
|------|--------|------|
| **单号 QPS** | ≤ 0.5（约 2s 一次），突发不超过 2 | 模拟人类对话节奏；SSE 流式本身耗时 |
| **单号并发** | 1（同一号不并发多会话） | 同号并发是明显非人行为 |
| **单号日调用上限** | 对齐 `daily_question_limit` 配额，预留 20% 余量 | 【实证】渲染层有 `daily_question_count/limit` 字段 |
| **整池 QPS** | 号数 × 单号 QPS，但同 IP 出口的总 QPS 单独限到 ≤ 2 | 防止同 IP 高并发 |
| **调用间隔抖动** | 每次请求间隔加 ±30% 随机抖动 | 破除"定时器式"规律性 |
| **夜间静默** | 【可选】凌晨 2-6 点降频到 0.1 QPS | 模拟真人作息，降低"24h 在线"信号（心跳已暴露在线，调用频率别再暴露） |

> 注意：心跳 60s 已经让服务端知道"设备 24h 在线"，这一点无法伪装（官方客户端就是常驻）。所以**调用频率要像真人，但在线时长不用伪装**——重点是别让"调用频率"也看起来像机器。

## 5. 冷却与熔断规则（对接 AgentHub 冷却表）

结合 AgentHub 已有的冷却表机制，为小浣熊定义冷却规则。**冷却触发源 = HTTP 状态码 + 业务错误码 + 客户端状态码**三类。

### 5.1 冷却规则表

| 触发条件 | 来源 | 冷却动作 | 冷却时长 | 是否换号 |
|---------|------|---------|---------|---------|
| **HTTP 401** | refresh 或 heartbeat【实证 auth.py:265 / desktopTrustedDeviceManager.js:201】 | 该号标记 `authentication_required`，进冷却 | 直到人工重新登录（长冷却） | ✅ 立即换号 |
| **HTTP 402** | 积分不足（推测，points 体系） | 该号进冷却 | 到次日配额重置 / 充值后 | ✅ 换号 |
| **HTTP 429** | 限流【推测】 | 该号冷却 | 60s ~ 5min，指数退避 | ✅ 换号，且同 IP 其他号也降速 |
| **HTTP 5xx** | 服务端故障 | 该号短冷却 | 30s ~ 2min，指数退避 | 🟡 换号重试，同号可快速恢复 |
| **`device_session_mismatch`** | 设备冲突【实证 desktopTrustedDeviceManager.js:286-288】 | 该号标记 `device_mismatch`，进冷却 | 需重新 bind（中长冷却） | ✅ 换号，并检查是否 clientDeviceId 被撞 |
| **`HostedAuthRequiredError` / "登录态已过期，请重新登录"** | refresh 401【实证 auth.py:246】 | 该号标记失效 | 直到重新登录 | ✅ 换号 + 告警 |
| **连续 N 次超时/网络错** | 网络层 | 该号冷却 | 2min，指数退避 | 🟡 换号 |
| **积分余额 = 0** | `points/v1/balance` 巡检 | 该号冷却 | 到充值/重置 | ✅ 换号 |

### 5.2 熔断（池级）

| 熔断条件 | 动作 |
|---------|------|
| 同 IP 出口下 ≥ 50% 的号在 5min 内连续 429 | **熔断该 IP 出口**，切换备用代理，该 IP 冷却 30min |
| 同一 clientDeviceId 下 ≥ 2 个号同时 `device_session_mismatch` | **熔断该 clientDeviceId**，告警——说明指纹没隔离干净，需重新生成 |
| 整池 ≥ 30% 的号同时 `authentication_required` | **池级告警**——可能是服务端批量风控或 token 批量过期，暂停调用人工排查 |

### 5.3 指数退避参数建议

```
冷却时长 = base × 2^retryCount + jitter
- 429/5xx:    base=30s, 上限 10min
- 超时:       base=60s, 上限 15min
- 401/登录失效: 不退避，直接长冷却等人工
```

## 6. 登录态健康度巡检与掉线兜底

### 6.1 巡检探针（按成本从低到高）

| 探针 | 接口 | 频率 | 能测出什么 |
|------|------|------|-----------|
| **本地 JWT exp 解析** | 不发请求，直接解 access_token payload 的 `exp` | 实时 | access_token 是否快过期（< 300s 触发刷新）【实证 auth.py:30】 |
| **余额探针** | `GET /api/web/points/v1/balance` | 每 30min | token 是否存活 + 积分是否充足 |
| **配额探针** | 读配额字段（`daily_question_count/limit`） | 每 30min | 是否快到日限额 |
| **refresh 探针** | `POST /api/web/auth/v1/refresh` | 每日 1 次 | refresh_token 是否还有效（30 天有效期）【00-总纲】 |
| **心跳探针** | `devices_current_heartbeat` | 每 60s（沿用官方心跳） | 设备绑定是否还有效、token 是否存活 |

> 巡检优先级：**本地 exp 解析（零成本）> 余额探针（低成本）> refresh 探针（每日一次验证 refresh_token）**。心跳本身就是持续的活探针，失败即掉线信号。

### 6.2 健康度状态机

```
healthy ──exp<300s──▶ refreshing ──成功──▶ healthy
   │                      │
   │                      └──失败(401)──▶ dead（告警+换号）
   │                      └──失败(5xx)──▶ degraded（退避重试）
   ├──心跳 device_session_mismatch──▶ device_mismatch（重新 bind 或换号）
   └──余额=0 / 配额用尽──▶ exhausted（冷却到重置）
```

### 6.3 掉线兜底与告警

| 掉线类型 | 检测信号 | 兜底动作 |
|---------|---------|---------|
| **access_token 过期** | 本地 exp 解析 | 自动 refresh【实证 auth.py `refresh_hosted_auth_token_if_needed`】，无需告警 |
| **refresh_token 过期/失效** | refresh 返回 401【实证 auth.py:265】 | 标记 dead，**告警**（需人工重新登录补号），换号 |
| **设备绑定失效** | 心跳 `device_session_mismatch` | 尝试重新 bind 一次；再失败则告警换号 |
| **积分耗尽** | 余额探针 = 0 | 冷却到重置，告警（提示充值或补新号） |
| **批量掉线** | 短时多号 dead | **池级告警**，暂停调用，排查是否被批量风控 |

## 7. 账号导入方式与 token 续期

### 7.1 导入方式对比

| 方式 | 流程 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| **手动粘 token** | 用户从官方客户端 `~/.box-agent/config/auth.json` 复制 `access_token`+`refresh_token` 粘贴入池 | 最简单，零开发 | access_token 3h 过期，必须连 refresh_token 一起给 | 小规模、测试 |
| **auth.json 导入** | 直接读取/上传整个 auth.json 文件 | 字段完整（含 refresh_token、office_identity） | 需要用户能找到文件 | **推荐**，中等规模 |
| **OAuth 登录导流** | 复现 `/code/authorize` → 深链 `office-raccoon://auth/callback?code=` → `login_with_authorization_code`【00-总纲】，号池内置登录页引导用户授权 | 自动化程度最高，可批量 | 开发量大，需处理深链回调 | 大规模、长期运营 |

> **推荐组合**：初期用 **auth.json 导入**（成本最低、字段最全），规模化后做 **OAuth 导流**。

### 7.2 token 续期机制

- 【实证】access_token ≈ 3h，refresh_token ≈ 30 天，刷新窗口 300s【00-总纲 + auth.py:30】。
- 【实证】刷新接口 `POST /api/web/auth/v1/refresh`，body `{"refresh_token": "..."}`，成功后返回新 `access_token`（可选新 `refresh_token`），并写回 auth.json【auth.py:282-300 / auth2.dis.txt:1381-1478】。
- **号池续期策略**：
  1. 每号独立存 `access_token + refresh_token + exp`。
  2. 后台任务扫所有号，`exp - now < 300s` 就调 refresh（与官方窗口一致）。
  3. **刷新相位加抖动**：多号不要在同一秒齐刷，每个号的刷新时刻加 ±60s 随机偏移，避免"同机批量刷新"特征。
  4. refresh 返回新 refresh_token 时**立即更新**（refresh_token 可能轮换）。
  5. refresh 401 → refresh_token 也死了 → 标记 dead，告警人工补号（30 天有效期意味着**至少每 30 天要人工干预一次**，除非官方客户端保持活跃自动续）。

> 【推测】refresh_token 30 天有效期是号池的"保质期天花板"——**超过 30 天不登录的号必然掉线**。所以号池要么定期用官方客户端登录保活，要么接受 30 天轮换补号。

## 9. 给 AgentHub 的落地清单（优先级排序）

1. **P0 — clientDeviceId 每号独立**：号池给每个账号生成并固定独立 `clientDeviceId`，调 box-agent 时用 `ClientInfo.from_meta` 注入，或每号独立 identity 文件。**不做这条，其余都白做。**
2. **P0 — 每号独立 bind + 心跳**：独立 `devices_current_bind`、独立 60s 心跳（相位抖动）。
3. **P0 — 关闭/隔离遥测**：池化模式不发 `/api/web/b/v1/m`，尤其关掉 skillHub 使用上报（它用真实 clientDeviceId）。
4. **P1 — 代理池 + 号-IP 绑定**：>3 号必须配，号与 IP 一对一绑定。
5. **P1 — 冷却熔断规则**：按 §5.1/5.2 接入 AgentHub 冷却表，重点处理 401 / device_session_mismatch / 429。
6. **P1 — 健康度巡检**：本地 exp 解析 + 每 30min 余额探针 + 每日 refresh 探针 + 心跳活探针。
7. **P2 — 节奏控制**：单号 ≤0.5 QPS、单号并发 1、间隔抖动 ±30%、对齐日配额。
8. **P2 — 导入与续期**：初期 auth.json 导入，规模化后 OAuth 导流；refresh 相位抖动 + refresh_token 轮换更新；记住 30 天保质期天花板。

> **底线**：小浣熊防伪强度中低（无混淆/无签名/无 pinning），**唯一的硬关联锚点就是 clientDeviceId 和 IP**。把这两个按号隔离干净，再关掉遥测，号池关联风险可降到很低。

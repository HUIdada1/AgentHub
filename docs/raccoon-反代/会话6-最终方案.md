# 商汤小浣熊 · 号池反代最终方案（第 6 轮合并）

> 本方案由 6 个相互独立的审查会话合并而成：
> 会话1 认证与令牌 / 会话2 指纹防伪设备绑定 / 会话3 LLM 调用接口与流式 / 会话4 积分余额配额 / 会话5 号池风控反关联。
> 目标：把小浣熊多个账号接入 **AgentHub 号池**，做成一个与 trae/workbuddy 平级的新渠道 `raccoon`，支持多号轮换、指纹透传、余额查询、风控反关联。
>
> **技术定性**：小浣熊防伪强度**低**（无签名/无 HMAC/无混淆/无证书 pinning），全部要素可静态复刻。唯一硬关联锚点是 **clientDeviceId + 出口 IP**。

---

## 0. 先看这段：能不能做、难在哪

**能做，而且不难。** 小浣熊 LLM 上行就是**纯 OpenAI Chat Completions 协议**（上游疑似 LiteLLM 网关），鉴权就是一个 JWT，防伪三件套（JWT + 设备指纹 + 受信设备绑定）全部已被静态复刻。

**真正的难点不在"反代协议"，而在"号池化"**：把 N 个号塞进同一台机器同一个出口，如何不被服务端用 `clientDeviceId` 和 IP 关联后批量封。本方案的核心工作量在指纹隔离与风控规避，不在协议对接。

**三个必须记住的硬约束**：
1. **30 天保质期天花板**：refresh_token 有效期约 30 天，超过 30 天不活跃的号必然掉线，号池要么定期保活要么接受轮换补号。
2. **能多开**：同一账号多个实例共用一份凭据没问题（刷新接口幂等、客户端容忍并发、无会话独占检测），但**同账号两次独立登录（两个 sid）有互踢风险**——所以一个号只登录一次，把 refresh_token 复制进池子共用。
3. **唯一硬锚点**：把 `clientDeviceId` 和出口 IP 按号隔离干净，再关掉遥测上报，连坐风险就降到很低。

## 1. 总体架构

```
                        ┌─────────────────────────────────────────────┐
   下游调用方            │              AgentHub 反代网关               │
  (你的 IDE / 脚本 /     │                                              │
   其他 AI 工具)   ───▶  │  OpenAI 兼容入口  /v1/chat/completions       │
   Authorization:       │         │                                    │
   Bearer <池内Key>      │         ▼                                    │
                        │  ┌──────────────────────────────┐           │
                        │  │  raccoon 渠道适配器            │           │
                        │  │  (adapters.cjs 新增)          │           │
                        │  │  · 选号(pool.cjs)             │           │
                        │  │  · 指纹注入(每号独立)           │           │
                        │  │  · 冷却/换号(rules)           │           │
                        │  └──────────────┬───────────────┘           │
                        │                 │ 带完整 x-client-* + JWT    │
                        └─────────────────┼───────────────────────────┘
                                          ▼
                          https://xiaohuanxiong.com/api/web/llm/v2
                                          （真实上游，经代理出口）
```

**关键设计决策**：
- **复用 AgentHub 现有号池骨架**：`adapters.cjs`（渠道适配）+ `pool.cjs`（选号/冷却）+ `credits.cjs`（余额）+ `store.cjs`（账号存储）+ `rules/headers.json`（指纹头配置）。新增一个 `raccoon` 适配器即可，不动主干。
- **不跑官方 Electron/box-agent**：直接在 Node 层用 `fetch` 调上游，指纹头由适配器按号注入（复刻 `ClientInfo.from_meta` 的六头逻辑），无需启动 Python。这样号池是纯 Node、轻量、可多开。
- **下游对 AgentHub 用池内 Key 鉴权**，AgentHub 对上游用池内账号的真实 JWT 鉴权——天然实现"一套池子对多下游发 key"。

## 2. 账号接入与令牌管理（来自会话1）

### 2.1 接入方式（三选一，按规模）

| 方式 | 流程 | 适用 |
|---|---|---|
| **auth.json 导入（推荐起步）** | 上传/粘贴官方客户端 `~/.box-agent/config/auth.json`，提取 `access_token`+`refresh_token`+`office_identity` | 小中规模，字段最全，成本最低 |
| 手动粘 token | 粘贴 access+refresh 两串 | 测试 |
| OAuth 导流 | 复现 `/code/authorize`→深链→`login_with_authorization_code` | 大规模长期运营，开发量大 |

> **一个号只登录一次**，把 refresh_token 复制进池。不要同号多处独立登录（会产生多个 sid，互踢风险）。

### 2.2 每号独立令牌池数据结构（存进 AgentHub store）

```ts
interface RaccoonAccount {
  id: string;                 // 池内 ID
  label: string;
  channel: "raccoon";
  // 凭据
  accessToken: string;
  refreshToken: string;
  officeIdentity: string;     // "personal" 或团队 org code
  accessExp: number;          // 本地解码 exp（不验签）
  refreshExp: number;
  sid: string;                // JWT payload.sid，"被顶号"自检 + 账号去重
  // 指纹画像（见 §3）
  deviceId: string;           // clientDeviceId，入池生成后固定
  deviceName: string;
  clientPlatform: string;     // "desktop-windows-x64"
  osVersion: string;          // "10.0.26200"
  ua: string;
  proxy?: string;             // 绑定的出口代理（见 §5）
  // 状态
  status: "ready"|"refreshing"|"degraded"|"expired"|"device_mismatch";
  generation: number;         // 每次成功刷新 +1
  lastError?: string;
  // 余额缓存（见 §6）
  credits?: number;
  expiresAt?: number;
}
```

> ⚠️ **两个坑**（会话1实证）：
> ① 若用官方 box-agent 跑，Electron 侧环境变量是 `BOX_AGENT_CONFIG_DIR`、box-agent 侧是 `BOX_AGENT_HOME`，**不同名，隔离时两个都要设**。
> ② Electron 刷新会**抹掉 auth.json 里的未知字段**——账号元数据绝不能塞进 auth.json，必须放池索引（本方案的 AgentHub store）。

### 2.3 集中刷新调度（池管理器独占刷新）

- **池管理器是唯一刷新者**，每 60s 扫一遍账号，对 `accessExp - now < 600s` 的号调 `POST /api/web/auth/v1/refresh`（body 仅 `{refresh_token}`），结果原子写回。**业务请求永远拿到 ready token**，避开惰性刷新的 15s 首请求延迟。
- **单飞防并发**：每号一把内存锁（复用 AgentHub 的 `refreshTokenLocked`）。
- **防串号自检**：刷新后解码新 access 的 `sid`，与登记值比对；不一致 = 被顶号，置 `degraded` 告警。
- **旋转竞态兜底**：若 refresh 返回 401，**重读一次最新 refresh_token 再试一次**（可能已被并发刷新旋转）。
- **失效兜底**：refresh 401 → 标记 `expired` 摘除 + 告警（需人工补号）；5xx/超时 → 指数退避（60s/5min/30min），旧 access 未过期期间继续可用。

## 3. 指纹与防伪完整复刻（来自会话2，已修正总纲误判）

### 3.1 防伪三件套（要复刻的全部）

| 层 | 机制 | 复刻要点 |
|---|---|---|
| 1 | `Authorization: Bearer <access_token>`（JWT HS256） | 池内真实 token |
| 2 | `x-client-*` 六个指纹头 | 每个 LLM 请求带，见 §3.2 |
| 3 | 受信设备绑定 + 60s 心跳 | **仅移动端连接器链路需要；纯 LLM/points 调用不触发**（会话1实证：LLM 头里没有 X-Client-Device-ID，设备绑定是旁路校验） |

> **会话1 的关键发现**：**只做 LLM/points 反代时不触发设备绑定校验**——`X-Client-Device-ID`（大写）是受信设备接口的头，LLM 只带小写 `x-client-device-id`（遥测性质）。所以**心跳/绑定对纯对话反代非必需**。但如果要模拟完整桌面端行为（或担心未来服务端收紧），可选择性实现绑定+心跳。

### 3.2 x-client-* 六头精确取值（号池每号注入）

| Header | 取值规则 | 号池取值建议 |
|---|---|---|
| `x-client-name` | 常量 `raccoon-ai` | **永远 `raccoon-ai`** |
| `x-client-platform` | `desktop-{os}-{arch}`（**带架构**） | 每号固定一个，90% 用 `desktop-windows-x64` |
| `x-client-version` | semver，服务端 `removeprefix('v')` 后发 `1.0.35` | 固定 `1.0.35`（跟随最新版，全号同版本是自然的） |
| `x-client-os-version` | `os.release()` | 每号从真实 Win build 池采：`10.0.26200/26100/22631/19045` |
| `x-client-channel` | 常量 `official` | **永远 `official`**（改了反而异常） |
| `x-client-device-id` | `desktop-device-identity.json` 的随机 UUID v4 | **每号一个随机 UUID，入池固定不变** |

> 清洗规则：仅保留 ASCII 可打印字符、≤256 字节（非 ASCII 整体置空）。
> ⚠️ 会话2 实证：box-agent 链路 platform 是 `desktop-windows-x64`（带架构），受信设备头 `X-Client-Platform` 是 `desktop-windows`（不带架构）——**两条链路格式不同，别混**。

### 3.3 会话关联头（彩蛋，必须处理）

LLM 请求还带 4 个会话关联头（`llm/base.pyc _agent_headers`）：
```
X-RACCOON-Session-ID / X-RACCOON-Turn-ID / X-RACCOON-Title / X-RACCOON-Call-Kind
```
**反代策略**：每次下游会话生成随机 UUID 作 Session/Turn ID，Title 可留空或随机短串，Call-Kind 透传或置默认。**跨号不复用同一组 ID**（否则成为跨号关联证据）。

### 3.4 设备指纹（如需绑定/心跳）

`clientDeviceId` 就是 `crypto.randomUUID()` 的随机 UUID v4（**非硬件派生**），持久化在 `desktop-device-identity.json`。号池给每号生成一个独立 UUID 固定即可。**不要在 device_id 里编码序号/日期/IP**（如 `dev-001`）——服务端熵分析会识别为伪造。

### 3.5 遥测（建议关闭）

- `desktopAnalytics` 的 `machine_id` 是**全局硬编码常量** `simulator-f31d...`（所有客户端相同，无区分能力，威胁小）——**修正了总纲里"来自 fingerprintjs"的误判**。
- **但 skillHub 上报用的是真实 clientDeviceId**（`skillHubManager.js:281-296`）——**必须关**，否则每用一次技能就上报一次设备 ID。
- 渲染层**没有实质浏览器指纹采集**（fingerprint 命中全是编辑器语法高亮和 FNV 文本 hash）。
- **结论：池化模式整个关掉遥测上报（不发 `/b/v1/m`）**。

## 4. LLM 调用与流式透传（来自会话3）

### 4.1 上游协议（纯 OpenAI 兼容）

- 端点：`POST https://xiaohuanxiong.com/api/web/llm/v2/chat/completions`
- 流式：标准 SSE，`stream:true` + `stream_options:{include_usage:true}`，**usage 在末尾带 usage 字段的 chunk 里**（客户端从 `chunk.usage` 读，不本地估算）。
- 默认模型 `raccoon-chat-ml-5-5`，别名 `raccoon-chat`/`raccoon-chat-ml` → 同名。
- **对默认模型且 thinking 关闭时，不传任何 reasoning/extra_body**（推翻总纲印象）。`extra_body` 双层嵌套只在 deepseek/doubao/qwen 分支，线上实为单层（LiteLLM 风格）。
- SenseNova 方言（XML 伪 tool_calls、reasoning_content 回放）**全是客户端后处理**，反代 **1:1 透传即可，无需实现**。

### 4.2 反代要实现的端点最小集

```
POST /api/web/llm/v2/chat/completions   # OpenAI 兼容，SSE + 末尾 usage chunk（核心）
GET  /api/web/llm/v2/model_catalog      # 模型目录（含计费倍率）——用于号池模型列表
POST /api/web/llm/v2/images/gen         # 文生图（可选）
```

### 4.3 请求/响应处理要点

| 项 | 处理 |
|---|---|
| `messages` | 原样透传（可能含 `reasoning_content`/`reasoning_details` 两种 thinking 回放形态，上游要消化或忽略） |
| `model` | 接受 `raccoon-chat-ml-5-5`/`raccoon-chat`/`raccoon-chat-ml` 别名，映射到上游同名 |
| `stream`/`stream_options.include_usage` | 原样透传，**务必让末尾 usage chunk 透传**（否则客户端计量为 0） |
| `tools` | 原样透传（标准 OpenAI function schema） |
| `max_tokens` | 透传（hosted 默认 80000） |
| 请求体大小 | 官方 hosted 限 10MB 本地预检；反代侧按需兜底 |

### 4.4 流式不断流 + 计费保护

1. **usage chunk 必须透传**，吞了客户端计量为 0。
2. SSE 原样转发，不缓冲整段。
3. **断流语义**：客户端"打开流失败"会整请求重试（最多 4 次指数退避 1s→60s）；"中途断流"不重试。**反代自己重连上游要注意：同一 prompt 重发 = 上游重复生成/扣费**，别盲目重试。
4. `finish_reason` 的 `length`/`max_tokens`/`tool_calls` 不要改写（客户端靠它做 tool 参数闭合修复）。

### 4.5 错误码 → 冷却/换号映射（关键）

| 错误 | 含义 | 处理 |
|---|---|---|
| HTTP 401 / body code `200003` | 授权失败（authorization_verify_error） | 刷新 token 重试一次；再败 → 换号 + 该号 refresh |
| body code `1000007` / insufficient_points | **积分不足** | 换号 + 该号冷却到积分重置 |
| HTTP 429 | 限流 | 换号 + 指数退避 60s~5min + 同 IP 其他号降速 |
| HTTP 5xx / 超时 | 服务端故障 | 换号重试 + 短冷却（30s~2min） |
| `device_session_mismatch` | 设备冲突 | 换号 + 检查 clientDeviceId 是否被撞 |
| HTTP 403 / permission | 无权访问模型 | 换号 + 标记该号无此模型权限 |

## 5. 号池风控与反关联（来自会话5）

### 5.1 隔离优先级（按连坐风险从高到低）

| 优先级 | 隔离项 | 做法 |
|---|---|---|
| **P0** | clientDeviceId | 每号一个随机 UUID，入池固定，永不中途更换 |
| **P0** | 受信设备绑定 | 若做绑定，每号独立 bind 不复用 device_id |
| **P0** | 关遥测 | 不发 `/b/v1/m`，尤其关 skillHub 上报 |
| **P1** | 出口 IP | >3 号必须代理池，号-IP 一对一绑定 |
| **P1** | 心跳相位 | 若做心跳，60s ± 15s 抖动，相位错开 |
| **P1** | 冷却熔断 | 接入 AgentHub 冷却表（见 §4.5） |
| **P2** | UA / os_version / device_name | 每号错开（拟真分布） |
| **不变** | channel=official、name=raccoon-ai | 常量，改了反而异常 |

### 5.2 出口 IP 策略

- 无证书 pinning/无签名，网络层只剩 IP 一个关联维度。**>3 号必须配代理池**。
- **号-IP 一对一绑定**（真人家里 IP 相对稳定），只在 IP 失效时换，比"每次随机 IP"更像真人。
- 实在没代理池：把并发压到极低 + clientDeviceId 独立更要做干净。
- **池级熔断**：同 IP 出口下 ≥50% 的号 5min 内连续 429 → 熔断该 IP，切备用代理，该 IP 冷却 30min。

### 5.3 调用节奏（保守，对齐配额）

| 维度 | 建议值 |
|---|---|
| 单号 QPS | ≤ 0.5（约 2s 一次），突发 ≤ 2 |
| 单号并发 | 1（同号不并发多会话） |
| 单号日上限 | 对齐 `daily_question_limit`，预留 20% 余量 |
| 同 IP 总 QPS | ≤ 2 |
| 间隔抖动 | ±30% 随机 |
| 夜间静默（可选） | 凌晨 2-6 点降频 0.1 QPS |

> 心跳已让服务端知道设备 24h 在线，在线时长不用伪装；**重点是调用频率要像真人**。

### 5.4 健康度巡检（成本从低到高）

1. **本地 JWT exp 解析**（零成本，实时）：access 快过期触发刷新。
2. **余额探针** `GET /points/v1/balance`（每 30min）：token 存活 + 积分充足。
3. **配额探针** 读 `daily_question_count/limit`（每 30min）：是否接近日限额。
4. **refresh 探针**（每日 1 次）：验证 refresh_token 有效。
5. **sid 比对**：每次刷新比对 sid，突变 = 被顶号告警。

## 6. 积分/余额查询接入号池（来自会话4，用户点名要）

> 关键事实：**积分/配额查询全在渲染层**，主进程和 box-agent 都不参与。统一信封 `{code, data}`，鉴权 `Authorization: Bearer`。

### 6.1 余额/配额相关端点全表（均有实证）

| 用途 | 方法 + 路径 | 关键返回字段 |
|---|---|---|
| **积分余额** | `GET /api/web/points/v1/balance` | `available_points`(总可用，号池排序主键)/`daily_points`/`monthly_points`/`reward_points`/`topup_points`/`topup_frozen` |
| 积分明细 | `GET /api/web/points/v1/bills?paging.limit=N&type={all\|expense\|income}&cursor或paging.offset` | `items[]` 含 `biz_type/event_name/points(正负)/created_at/grant_at/expire_at/biz_id` |
| **账户配额** | `GET /api/web/office/v3/setting_info`（团队 `/api/web/org/user/office/v1/setting_info`） | `daily_question_count/limit`、`daily/monthly_web_search_count/limit`、`used/total_space_mb` 等 |
| 套餐状态 | `GET /api/web/auth/v1/entitlement_info` | `office.pro_enable`、`type/provider_type/auto_renew_status/subscription_expired_at` |
| 用户信息 | `GET /api/web/auth/v1/user_info` | `pro_office_enabled`、`is_office_university_applied`、`orgs[]` |
| **登录送积分（每日签到）** | `POST /api/web/desktop/v1/login/points/grant`（头 `X-Client-Platform/Version`） | `data.granted`（本次是否新发放） |

### 6.2 业务规则（影响号池策略）

- **消耗顺序**：每日额度 → 每月额度 → 奖励积分 → 加油包（先到期先用）。
- **免费版每日 300 积分**，升级版 500/日 + 10000/月；加油包永久有效但退订冻结。
- **每日积分默认当日 24:00 清零，但当天登录后延长至 7 天**——所以**每日必须至少登录/签到一次**才能锁定当日积分。
- **登录送积分幂等**：每次进应用触发一次 `grant`，`granted=true` 才是新发放。号池可每日定时给每号调一次 grant 当"自动签到保活"（既锁积分又维持活跃）。
- 明细只保留 3 个月，有分钟级同步延迟。

### 6.3 余额页数据结构（映射进 AgentHub 号池）

```ts
interface AccountBalance {
  accountId: string;
  availablePoints: number;     // balance.available_points ← 排序主键
  daily/monthly/reward/topupPoints: number;
  topupFrozen: boolean;
  isPro: boolean;              // entitlement.office.pro_enable
  planLabel: "free"|"personal-pro"|"education"|"alipay"|"unavailable";
  subscriptionExpiredAt?: string;
  dailyQuestion: { used: number; limit: number };      // setting_info
  webSearch:   { used: number; limit: number; period: "day"|"month" };
  quotaExhausted: boolean;     // daily_question 用尽 或 联网超限
  fetchedAt: number;
}
```

### 6.4 单账号采集流（每号 3 GET + 1 POST，先签到再查）

```
POST /api/web/desktop/v1/login/points/grant   # 先薅当日积分（幂等）
GET  /api/web/points/v1/balance               # 余额 6 字段
GET  /api/web/office/v3/setting_info          # 配额 + 冗余 available_points
GET  /api/web/auth/v1/entitlement_info        # 套餐 pro_enable/订阅
（可选）GET /api/web/auth/v1/user_info         # 大学认证/orgs
```
全部带 `Authorization: Bearer` + 该号的 `X-Client-Platform/Version/Device-ID`。采集前先确保 token 已刷新。

**轮询建议**：余额 5~10min（积分只在对话后变，触发式刷新更省）；配额每次任务后刷；grant 每日 00:00 后首采调一次（用 granted 判重）。逐账号串行或低并发 ≤4，账号间错开。

### 7.2 复用现有抽象（不用重造）

- **账号级稳定指纹**：AgentHub 已有 `deviceIds(account)` = `sha256("agenthub:"+purpose+":"+uid)` 派生固定 id（workbuddy 的 x-machine-id 就这么来的）。raccoon 的 `clientDeviceId` 用**同模式**：入池时对每号 `crypto.randomUUID()` 生成一次并存库（注意 raccoon 要的是**随机 UUID**不是 hash 派生，因为官方就是 randomUUID）。
- **指纹白名单对齐打法**：WorkBuddy 过 11128 渠道白名单就是靠逐字段对齐官方桌面端头组。raccoon 的六头照搬这套"逐字段对齐官方值"的打法。
- **401 就地刷新 + 单飞**：`refreshTokenLocked` 现成。
- **冷却表**：现成，按 §4.5 配错误码。

## 8. 投产前必须实测确认的项（各会话未确认清单汇总）

静态分析覆盖了 95%，以下 6 项只能靠抓包/实测坐实，**投产前用小号验证**：

1. **refresh 旋转后旧 refresh 是否立即失效**（连续刷两次，第二次用旧 refresh 看是否 401）。

## 9. 风险与合规提示

- **这是对你自己持有的账号做反代**，属个人自动化/互操作范畴。但注意：
  - 多账号批量薅每日签到积分、绕过设备数限制，**大概率违反商汤小浣熊的用户协议**（账号仅限本人本设备使用）。被检测到最坏结果是封号。
  - 别把池子对**外**提供付费服务（二次分发商用 LLM 能力风险更高）。
- **30 天保质期是硬约束**：号池必须有"定期保活"或"轮换补号"机制，否则批量掉线。
- **数据安全**：auth.json 含完整 refresh_token（30 天有效），入库/备份要加密，别明文进 git。
- **兜底心态**：即便指纹隔离做得再干净，同 IP 多号仍有残余关联风险。号池规模越大越要配代理池。

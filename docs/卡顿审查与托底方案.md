# 卡顿与卡死审查方案（反代网关 / 记忆中枢）

> 2026-09-29 审查 · 针对"号池 zcode 阿里云弹窗加载不完导致卡死"及同类问题的系统性排查与整改基线。
> 本文档是整改的唯一执行依据：问题清单 → 托底矩阵 → 整改批次 → 回归核对表。

---

## 一、根因链（为什么会"卡死"）

```
主进程某 handler 挂起（网络无超时 / 弹窗等不到回调 / 事件永不触发）
  → 渲染进程 ipc.ts call() 的 await 永不 settle（call 本身无超时）
    → 页面 try/finally 里的 finally 永不执行
      → busy/loading 标志永久为真 → 按钮永久禁用 / 骨架屏永久转圈 / 弹窗关不掉
        → 用户观感：页面卡死
```

`try/finally` 只能兜住"出错"，兜不住"永不返回"。本次整改的核心就是打断这条链的每一环。

### 已确认的三处根因

| # | 位置 | 根因 |
|---|------|------|
| R1 | `electron/backend/proxy/zcodeCapture.cjs` | 阿里云验证码 SDK 走 `<script src="o.alicdn.com/...">` 加载，**无加载超时**；主进程 `solveCaptcha()` 只在 提交/失败/关窗/加载失败 四种回调时 resolve，**无总体看门狗**。网络挂起时弹窗永久停在"正在准备人机校验…"，Promise 永不返回——这就是"zcode 阿里云弹窗加载不完导致卡死"的直接根因 |
| R2 | `src/api/ipc.ts` `call()` | 所有 IPC 调用无超时，主进程任何挂起都会原样传导到渲染端，全应用 20+ 处 busy/loading 标志随之永久卡死 |
| R3 | `electron/backend/proxy/index.cjs` `checkinBatch` | 签到二段流内联 `await zcodeCapture.solveCaptcha(...)`，R1 挂起时整个批量签到被堵死，`checkinBusy` 永久为真 → 「一键签到/一键领取」永久禁用 |

### P2 — 体验与健壮性

| # | 位置 | 现象 |
|---|------|------|
| P2-1 | MemProgressDialog | running 永久时只有转圈，无"耗时异常"提示；`result` 为 null 时误显示 ✗ 失败 |
| P2-2 | ProxyAgentsView:859 / ProxyHomeView 骨架行 | `v-if` 与 `v-for` 同元素反模式 |

### 明确不改（防止过度工程）

- App.vue 全局动效（MutationObserver / 粒子 / 数字补间）：设计资产，非本次卡顿根因。
- ECharts（MemoryTrendChart）：已规范 dispose/resize，无需动。
- MemoryHeatmap 371 格：已做事件委托与 computed 缓存，量级可接受。
- 弹窗 Esc / focus-trap 等可访问性增强：不属于卡顿范畴。

## 三、托底矩阵（整改规则）

| 层 | 规则 | 实现 |
|---|------|------|
| 弹窗层 | 任何等待外部回调的窗口必须有**总体看门狗**，超时自动关闭并 resolve 失败 | zcodeCapture：页面 SDK 15s 加载超时 + 主进程 120s 看门狗 + `render-process-gone`/`unresponsive` 托底 |
| IPC 层 | `call()` 默认 45s 看门狗，超时 reject（只结束渲染端等待，不取消主进程任务）；**长任务白名单**显式传 0（它们各有主进程侧互斥/进度事件/取消 IPC 托底） | ipc.ts 第三参 `timeoutMs` |
| 页面层 | busy/loading 全部经 try/finally 复位（已有），R2 修复后 finally 必然执行 | 随 R2 自动生效 |
| 事件层 | 事件回调不得直接调重量级 refresh，必须经 **coalesce（合流）**：同刻只在跑一次 + 间隔内多次合并为末尾一次 | 新增 `src/utils/timing.ts` `coalesceAsync()` |
| 模板层 | 列表渲染用的派生数据必须 computed 化，禁止模板内每渲染 filter/map 重建 | ModelGatewayPanel / ProxyModelsView |
| 进度层 | 长任务弹窗超过阈值时长必须给"耗时异常"文案兜底 | MemProgressDialog `staleMs` |

### 长任务白名单（call 传 0 的理由）

`webdavSync`（整目录传输）、`proxyPoolsyncRun`（主进程有 running 互斥）、`proxyCheckinRun/proxyCheckinStatus`（逐账号串行 HTTP + 抖动，主进程 checkinBusy 互斥）、`proxyCreditsRefresh/proxyCreditsRefreshChannel/proxyAccountRefresh`（逐账号 60s 上限串行）、`proxyZcodeSolveCaptcha`（150s，主进程 120s 看门狗 + httpJson 60s 双托底）、`proxyModelsSync`（外网目录 60s 上限）、`memorySyncRun`（有取消 IPC + 进度事件）、`memoryImportApply/memoryImportPreview/memoryImportSourceDetect`（主进程后台跑 + 进度事件 + 取消 IPC）、`memoryDistillRun/memoryProfileGenerate/memoryDedupScan/memoryAutoTaskRun/memoryAutoReport`（调模型分钟级，进度弹窗托底）、`memoryExport/memoryExportZip`（大导出）、`memoryBridgeRestart/memoryAgentVerify/memoryAgentVerifyAll`（拉起桥进程）、`memoryProviderTest/memoryProviderFetchModels/memoryLlmTestCall`（真实网络调用，主进程 llm client 自带超时但三级连测可能超 45s）。

除白名单外一律 45s：超时后页面 toast 报错、标志复位——"永久卡死"降级为"可重试的超时错误"。

## 四、整改批次（执行顺序）

1. **批①（P0-1/3）** zcodeCapture.cjs：SDK 15s 加载超时、主进程 120s 看门狗、render-process-gone/unresponsive 托底、定时器统一收口到 done()
2. **批②（P0-2 及其余全部 P0）** ipc.ts call() 看门狗 + 白名单
3. **批③（P1-1~4）** utils/timing.ts `coalesceAsync` + 六个事件风暴点接入
4. **批④（P1-7/8）** ProxyHomeView 轮询重建先清旧 timer、copiedTimer 卸载清理；Sidebar memoryStats 三 IPC 并发化
5. **批⑤（P1-5/6）** ModelGatewayPanel `briefByProvider` computed、ProxyModelsView `modelsByChannel` computed（tabChannels 同步复用）
6. **批⑥（P2）** MemProgressDialog 耗时异常提示 + result 为空的中性文案；v-if/v-for 两处；ProxyKeysView watch(active) 兜底刷新；ImportView/SyncView 取消按钮补 catch

## 五、回归核对表（人工）

- [ ] 断网/拔网线后点 zcode「过码」：15s 内弹窗报"SDK 加载失败/超时"并自动关闭，按钮恢复
- [ ] 过码弹窗打开后放着不管：120s 自动关闭并提示超时，「过码」按钮恢复
- [ ] 过码弹窗打开时点「一键领取」其它账号：排队执行，互不取消
